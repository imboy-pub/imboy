## 1. 文档用途

本文档保留的价值主要有三点：

1. 记录历史上曾集中暴露过的测试异味类型；

3. 作为“为什么要持续治理测试质量”的背景材料，而不是当前发布门禁清单。

## 3. 历史问题类型

### 3.1 占位式断言

典型表现：

- 直接写 `?assert(true)`；
- 只验证变量非空、类型正确；
- 测试名称与业务能力匹配，但没有实际断言结果。

### 3.2 宽松断言

典型表现：

- 只验证 `is_map/1`、`is_binary/1`、`is_integer/1`；
- 允许过宽的 `orelse` 分支，导致错误返回也能通过；
- 不验证关键字段、状态码、错误码和副作用。

### 3.3 假分支覆盖

典型表现：

- 写了 `case` 或 `receive`，但所有分支都返回成功；
- 只验证“能跑完”，不验证“是否跑对”；
- 遇到异常输入时没有断言期望错误。

### 3.4 未触达被测逻辑

典型表现：

- 测试只构造输入数据，不调用被测模块；
- 只 mock，不验证真实接口组合；
- 只验证 helper 常量，而不验证业务路径。

## 5. 当前仍适用的改进原则

### 5.1 先验证真实行为

每个测试至少应满足以下一项：

- 调用被测函数并验证返回值；
- 验证响应包体中的关键字段、状态码或错误码；
- 验证副作用，例如写库、发消息、状态变更、权限拦截；
- 验证异常路径，而不是只验证成功路径。

### 5.2 Mock 只用于隔离外部依赖

推荐使用 `meck` 隔离：

- 外部 HTTP / 第三方服务；
- 数据库或配置读取的不可控分支；
- 时钟、随机数、通知投递等副作用依赖。

不推荐把整个业务函数 mock 掉之后再断言“调用成功”，那样无法提供真实保护。

### 5.3 按层分清测试职责

- `EUnit`：函数级、模块级、契约级验证；
- `Common Test`：跨模块流程、时序、状态流转；
- 手工脚本：仅保留联调补充，不作为主门禁。

### 5.4 优先补最有交付价值的门禁

当资源有限时，优先顺序建议为：

1. 公共 / 后台接口契约与权限拦截；
2. 路由与模块开关一致性；
3. 登录、消息、群组、会话等主链路；
4. 高风险模块的 Repo / DS 行为；
5. 复杂流程与跨端联调场景。

## 6. 推荐改造方式

### 6.1 Handler / Middleware 测试

优先验证：

- 状态码；
- `code` / `message` / `payload` 结构；
- 权限不足、参数缺失、功能关闭等边界行为。

### 6.2 Logic / Repo / DS 测试

优先验证：

- 输入到输出的业务规则；
- 数据持久化与查询结果；
- 错误分支与兜底逻辑；
- 时间、排序、分页、过滤等容易回归的细节。

### 6.3 历史“假测试”改造策略

遇到旧测试时，推荐按以下顺序处理：

1. 删除无意义的 `?assert(true)`；
2. 补真实调用；
3. 补关键断言；
4. 若需要外部依赖，再补最小必要 mock；
5. 最后再决定是否拆成更细粒度测试。
