# Imboy 三端一期功能矩阵（可销售版本）

> Last Updated: 2026-03-08  
> Status: 长期产品基线文档  
> Related docs: `doc/guides/product-target-boundary.md`, `doc/guides/phase2-modularization-strategy.md`, `doc/guides/customer-acceptance-checklist.md`

## 1. 文档目的

本文档用于回答三个问题：

1. `Imboy` 一期到底应该卖什么；
2. 当前三端（`imboy` / `imboyapp` / `imboy-admin-frontend`）已经做到什么程度；
3. 哪些能力属于一期主线，哪些能力应作为二期模块保留而不是继续混在主包里。

本文档默认以“**可销售、可部署、可联调、可验收**”作为判断标准，而不是以“是否适合做大众社交 App”作为判断标准。

## 2. 一期定义

一期不是“功能最少版本”，而是“**最小可卖版本**”。

一期目标是把 `Imboy` 打包成一套可以向客户交付的 IM 解决方案，满足以下条件：

1. 客户能快速部署；
2. 客户能完成基础接入；
3. 客户能完成日常治理与运营；
4. 交付方能够通过文档和门禁进行支持，而不是完全依赖口头说明。

## 3. 判定规则

### 3.1 状态分级

- **已可销售**：三端主链路具备，已有测试或契约支撑，只差文档或轻量收口。
- **可作为高配销售**：能力已存在，适合按行业版或高级版出售。
- **二期模块**：代码资产已具备，不应删除，但默认不纳入一期主包。
- **暂不主推**：代码或页面虽存在，但对一期成交帮助有限，不应继续抢占主线资源。

### 3.2 三端说明

- **后端**：`imboy`，负责 API、WebSocket、存储、管理接口与测试。
- **客户端**：`imboyapp`，负责 Flutter App 页面、路由、状态与联调测试。
- **后台**：`imboy-admin-frontend`，负责运营管理、审核、统计、RBAC 与治理界面。

## 5. 现阶段最客观的判断

### 5.1 一期已经基本完成的部分

从三端代码现状看，以下结论成立：

1. 一期**不是缺核心功能**；
2. 一期的主链路已经不再是 Demo 级别，而是接近可交付级别；
3. 当前主要问题不是“继续补更多功能”，而是“把已有能力包装成产品”。

### 5.2 一期还没有完全闭环的部分

当前还需要补齐的主要是以下四类工作：

1. **文档闭环**：部署、联调、模块说明、功能矩阵、验收清单；
2. **模块边界**：把二期能力做成功能包，而不是默认主包；
3. **测试基座收口**：尤其是 App 端测试环境注入、通知链路、弱网回归；
4. **销售交付材料**：版本差异、可选模块、交付清单、FAQ。

### 5.3 对“一期状态”的最终结论

如果从“消费级社交 App 上线”角度判断，一期还不能算完成。

如果从“面向客户销售的 IM 解决方案”角度判断，当前三端能力已经达到：

**功能接近完成，产品化与交付文档成为主战场。**

## 6. 一期主包建议

建议将以下内容定义为默认销售主包：

1. 登录注册、鉴权、设备管理；
2. 单聊、群聊、会话、未读、ACK、离线消息；
3. 好友、黑名单、标签、搜索、`@mention`、收藏；
4. 群管理、群公告、群文件、群相册；
5. 举报、反馈、审核、审计与后台治理；
6. 部署、监控、日志、API 文档、联调手册。

## 7. 一期高配建议

建议将以下内容定义为高配能力，而不是基础包强绑定：

1. `E2EE` 及密钥恢复；
2. `Channel` 的通知、订阅、消息与管理能力；
3. AI 摘要、AI 搜索问答、AI 翻译（后续增值项）。

## 8. 二期模块建议

建议把以下内容明确转为二期模块，默认关闭、按场景交付：

1. `Location` 社交扩展；
2. `Moment` 内容扩展；
3. `Channel Discover / Invitation / Order` 商业化扩展；
4. `Group Vote / Schedule / Task` 群协作扩展。

这些能力当前已经有较明显的三端代码资产，因此正确动作不是删除，而是：

1. 建立功能开关；
2. 建立单独契约文档；
3. 建立单独测试门禁；
4. 在销售物料里作为可选模块列出。

## 9. 一期剩余重点工作

建议优先按以下顺序收口：

1. 完成三端功能矩阵与模块边界文档；
2. 补齐一期主包 API / 联调 / 部署文档；
3. 建立模块开关机制；
4. 修复 App 端测试基座问题并补发布门禁；
5. 整理 Demo、验收脚本和交付清单。
