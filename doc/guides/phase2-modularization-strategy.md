# Imboy 二期模块化设计与开关策略

> Last Updated: 2026-03-08  
> Status: 长期产品设计文档  
> Scope: 二期模块边界、默认关闭策略、三端开关与交付拆分方法  
> Related docs: `doc/guides/three-end-phase1-function-matrix.md`, `doc/guides/module-feature-flag-config.md`

## 1. 文档目的

本文档定义 `Imboy` 二期功能如何从“已经存在的三端能力”收束为“可按需开启的模块化产品”。

目标不是再做一套新的系统，而是把当前已有能力从“默认都混在一起”变成：

1. **主包可卖**；
2. **模块可选**；
3. **三端同步开关**；
4. **契约和测试独立**；
5. **销售和交付边界清晰**。

## 2. 模块化原则

### 2.1 基本原则

1. **代码保留**：已有功能不因为暂不主推而删除；
2. **默认关闭**：未购买或未启用的模块，不应在前台默认暴露；
3. **三端一致**：后端、客户端、后台必须由同一模块定义驱动；
4. **文档独立**：每个模块应有独立契约、说明和验收项；
5. **测试独立**：模块关闭时不影响主包门禁，开启时有独立回归；
6. **报价独立**：模块应可作为销售项或行业包。

### 2.2 模块层级

建议把产品能力分为三层：

1. **核心主包**：默认开启，构成标准 IM 解决方案；
2. **高配包**：默认关闭，按行业或版本启用；
3. **扩展模块**：按客户需求单独开启、测试、报价和交付。

## 3. 二期模块目录

### 3.1 模块 M1：`location`

**目标**：提供位置消息与附近的人能力。

**包含范围**：

1. 用户位置可见状态；
2. `people nearby` 页面；
3. 地图位置选择与位置消息；
4. 附近的人相关 API 与隐私开关。

**适用客户**：

1. 本地社群；
2. 同城活动；
3. 线下服务或导览场景。

**不建议默认开启原因**：

1. 与大多数私有部署客户主需求不一致；
2. 涉及定位权限与隐私合规；
3. 会提高移动端审核和合规复杂度。

### 3.2 模块 M2：`moment`

**目标**：提供朋友圈 / 动态内容能力。

**包含范围**：

1. 动态发布、删除、点赞、评论；
2. 动态时间线；
3. 动态举报与后台治理；
4. 动态相关 S2C 事件。

**适用客户**：

1. 社群互动；
2. 内部动态墙；
3. 会员社区内容扩展。

**不建议默认开启原因**：

1. 它会把产品从“IM 工具”拉向“内容社区”；
2. 治理和审核成本提升明显；
3. 一期成交价值不如主链路高。

### 3.3 模块 M3：`channel_commerce`

**目标**：在频道能力上叠加发现、邀请和订单闭环。

**包含范围**：

1. 频道发现页；
2. 频道邀请；
3. 频道订单、支付、订阅期；
4. 频道高级治理与统计。

**适用客户**：

1. 会员社群；
2. 付费订阅社区；
3. 创作者私域运营。

**不建议默认开启原因**：

1. 商业化链路会显著提高交付复杂度；
2. 涉及支付、订单、权限和状态一致性；
3. 更适合特定客户，而不是基础 IM 客户。

### 3.4 模块 M4：`group_productivity`

**目标**：为群提供轻协作能力。

**包含范围**：

1. 群投票；
2. 群日程；
3. 群任务；
4. 与群治理和消息提醒联动的扩展动作。

**适用客户**：

1. 班级 / 组织 / 轻项目组；
2. 活动组织和社群协作；
3. 有轻量协同需求但不想上重 OA 的客户。

**不建议默认开启原因**：

1. 它会增加 UI 复杂度与维护成本；
2. 容易分散一期主包的产品叙事；
3. 更适合作为“协作增强包”。

## 4. 三端统一开关设计

### 4.1 后端

后端作为最终授权源，建议在 `config_ds` 所读取的配置中增加统一 `features` 配置块。

建议的开关键如下：

- `features.location.enabled`
- `features.moment.enabled`
- `features.channel_discover.enabled`
- `features.channel_invitation.enabled`
- `features.channel_order.enabled`
- `features.group_vote.enabled`
- `features.group_schedule.enabled`
- `features.group_task.enabled`

后端职责：

1. 决定路由是否可用；
2. 决定接口是否直接返回“模块未启用”；
3. 决定后台接口和统计是否开放；
4. 作为三端配置的事实来源。

### 4.2 客户端

客户端不应再靠“是否有页面”来判断功能存在，而应建立统一 `FeatureRegistry`。

客户端职责：

1. 控制路由是否可进入；
2. 控制入口按钮是否展示；
3. 控制实验性模块是否显示在个人页、联系人页、频道页或群页；
4. 在模块关闭时给出稳定降级，而不是空白页面。

建议在 App 层增加：

1. `FeatureRegistry` 或 `FeatureProvider`；
2. 统一从服务端拉取模块配置；
3. 本地缓存模块配置用于离线展示控制。

### 4.3 管理后台

后台已经具备菜单配置和 RBAC 机制，因此最适合作为模块化第一落点。

后台职责：

1. 基于菜单配置隐藏模块页面；
2. 基于 RBAC 限制模块权限；
3. 在模块未启用时，不暴露相关运营入口；
4. 支持按版本输出不同菜单集。

## 5. 模块与版本包映射

建议形成如下打包方式：

### 5.1 基础版

默认开启：

1. 登录注册与设备；
2. 单聊 / 群聊 / 会话；
3. 群治理与后台治理；
4. 搜索、`@mention`、反馈、举报；
5. 基础部署与 API。

默认关闭：

1. `location`
2. `moment`
3. `channel_discover`
4. `channel_order`
5. `group_vote`
6. `group_schedule`
7. `group_task`

### 5.2 专业版

在基础版上可增加：

1. `channel` 基础通知和订阅；
2. `E2EE`；
3. 更强后台与审计；
4. 更完整的监控和运维能力。

### 5.3 行业扩展包

按需开启：

1. 同城社交包：`location`
2. 社群内容包：`moment`
3. 频道商业化包：`channel_discover` + `channel_invitation` + `channel_order`
4. 群协作包：`group_vote` + `group_schedule` + `group_task`

## 6. 模块化落地顺序

### 6.1 第一步：定义开关协议

需要先确定：

1. 配置结构；
2. 默认值；
3. 服务端下发格式；
4. 前台与后台读取方式。

### 6.2 第二步：控制入口而不是先删代码

优先做：

1. 入口隐藏；
2. 路由守卫；
3. API 失败兜底；
4. 菜单与权限收口。

不建议优先做：

1. 删除页面；
2. 删除 Handler；
3. 删除数据表；
4. 大规模重构现有实现。

### 6.3 第三步：补契约与测试

每个模块都至少要补三类文档：

1. 模块边界说明；
2. 三端接口契约；
3. 验收与回归清单。

每个模块都至少要补两类门禁：

1. 关闭状态门禁：确保关闭时不影响主包；
2. 开启状态门禁：确保打开后主链路可用。

## 7. 模块化验收标准

当一个模块满足以下条件，才算真正模块化完成：

1. 可在后端配置中独立开关；
2. 可在 App 中独立展示或隐藏；
3. 可在 Admin 中独立展示或隐藏；
4. 有独立契约文档；
5. 有独立回归项；
6. 有独立销售描述。

## 8. 与一期关系

二期模块化不是对一期的否定，而是对当前资产的正确包装。

当前已有代码基础说明：

1. 二期模块并非“从零开始”；
2. 正确动作不是继续混入一期主包；
3. 正确动作是把已有代码转成可控的产品包。
