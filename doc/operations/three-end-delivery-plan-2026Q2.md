# Imboy 三端产品化推进计划（2026 Q2）

更新时间：2026-03-07

状态：阶段性执行文档

说明：本文档属于当前阶段执行计划，阶段结束后可归档，不强制纳入长期文档主索引。

## 1. 阶段目标

在不继续扩张功能面的前提下，把 `Imboy` 现有三端能力收束为：

1. 可销售；
2. 可部署；
3. 可联调；
4. 可验收；
5. 可模块化扩展。

阶段目标不是“再实现更多功能”，而是“把现有功能变成可交付产品”。

## 2. 总体节奏

建议按 6 周推进。

### 第 1 周：一期边界与资料收口

交付物：

1. 产品目标与边界文档；
2. 三端一期功能矩阵；
3. 二期模块化策略；
4. 初版交付清单。

验收标准：

1. 一期主包、高配包、二期模块边界清晰；
2. 所有人对“先卖什么、后卖什么”达成一致。

### 第 2 周：一期文档闭环

交付物：

1. 部署文档补齐；
2. 联调文档补齐；
3. 客户验收清单；
4. FAQ / 版本说明 / 报价范围草案。

验收标准：

1. 客户可按文档独立完成基础部署；
2. 客户可按文档完成基础联调。

### 第 3 周：模块开关设计与后台先行

交付物：

1. 模块开关字段定义；
2. 后台菜单和权限的模块化方案；
3. 二期模块默认关闭策略；
4. 兼容性说明。

验收标准：

1. 后台菜单可以按模块隐藏；
2. 一期主包页面不再被二期功能干扰。

### 第 4 周：客户端与后端开关收口

交付物：

1. App 端模块注册表；
2. 后端模块配置读取与兜底响应；
3. 关闭态与开启态回归清单。

验收标准：

1. 模块关闭时不出现死链路或空白入口；
2. 模块开启时主链路稳定可用。

### 第 5 周：测试与门禁收口

交付物：

1. App 测试基座修复项；
2. 三端门禁与验收项统一；
3. 发布前回归清单。

验收标准：

1. 当前已知的测试基座问题有明确修复或绕行方案；
2. 三端可以输出统一的 PASS / FAIL / 风险结论。

### 第 6 周：销售与交付包装

交付物：

1. Demo 清单；
2. 功能对比表；
3. 标准交付清单；
4. 版本划分与模块报价说明。

验收标准：

1. 可以对外演示；
2. 可以对外报价；
3. 可以对外给出交付边界。

## 3. 工作流分组

### A 组：文档与产品包装

优先级：最高

任务：

1. 整理三端功能矩阵；
2. 整理主包 / 高配 / 模块边界；
3. 补齐部署与联调文档；
4. 形成客户验收清单。

### B 组：模块化与开关策略

优先级：高

任务：

1. 定义模块清单；
2. 定义后端开关键；
3. 定义客户端模块注册表；
4. 定义后台菜单与 RBAC 开关。

### C 组：测试与门禁

优先级：高

任务：

1. 修复 App 端测试基座问题；
2. 输出三端发布门禁清单；
3. 建立一期主包关闭二期模块后的稳定性回归。

### D 组：交付与销售材料

优先级：中高

任务：

1. 标准交付物清单；
2. 版本差异表；
3. Demo 演示脚本；
4. FAQ 与常见边界问题说明。

## 4. 阶段里程碑

### M1：一期定义冻结

完成标准：

1. 一期主包清单冻结；
2. 二期模块清单冻结；
3. 不再新增会影响叙事的横向功能。

### M2：文档可交付

完成标准：

1. 部署文档足够支撑独立部署；
2. 联调文档足够支撑客户端接入；
3. 客户验收清单可直接执行。

### M3：模块可控

完成标准：

1. 二期模块可独立关闭；
2. 关闭后二期入口不干扰主包；
3. 后台菜单和权限同步生效。

### M4：可演示可报价

完成标准：

1. 有标准 Demo 路径；
2. 有功能对比表；
3. 有交付边界说明；
4. 有版本与模块报价口径。

## 5. 当前优先级排序

当前最该做的不是继续写功能，而是按如下优先级推进：

1. 文档与边界；
2. 模块开关；
3. 测试基座与门禁；
4. 交付材料；
5. 再决定是否继续补二期模块体验。

## 6. 风险点

### 风险 R1：三端叙事不一致

表现：

1. 后端能力很多；
2. App 暴露入口很多；
3. 后台菜单很多；
4. 但销售与交付上讲不清楚主包边界。

处理方式：

1. 以模块清单为单一事实来源；
2. 以后台菜单和客户端入口为第一层收口点。

### 风险 R2：把二期模块继续当一期主线打磨

表现：

1. 功能越来越多；
2. 客户价值不更清晰；
3. 交付反而更难。

处理方式：

1. 一切新增工作先判断是否提高成交率；
2. 不提高成交率的功能优先降级到模块池。

### 风险 R3：测试问题被误判为业务问题

表现：

1. App 有部分失败来自插件注入与初始化；
2. 真实业务完成度被低估。

处理方式：

1. 单独修测试基座；
2. 把“业务未实现”和“测试环境失败”分开统计。

## 7. 阶段完成标志

当以下事项全部满足时，可认为本阶段结束：

1. 一期主包与二期模块边界冻结；
2. 三端功能矩阵完成；
3. 部署、联调、验收文档可用；
4. 二期模块具备明确开关策略；
5. 三端门禁能输出统一结论；
6. 对外演示和报价材料可用。
