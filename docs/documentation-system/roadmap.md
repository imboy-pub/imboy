# 文档体系落地路线图

> **类型**：指南 · **读者**：文档负责人 / 工程负责人 · **版本**：v1.0 · **最后更新**：2026-07-24

四个阶段，8 周见全貌。每个阶段有明确验收标准，不达标不进下一阶段。

---

## Phase 1 — 骨架（第 1-2 周）

> 目标：新分类结构上线，所有存量文档在门户页可达。

| # | 任务 | 产出 | 验收标准 |
|---|------|------|---------|
| 1.1 | 创建四象限目录骨架 | `docs/{tutorials,guides,reference,explanation}/` 各含 README 说明该目录定位 | 目录合入主干 |
| 1.2 | 重写 docs/README.md 为门户页 | 按「读者入口地图」组织的导航索引 | 从门户页 3 次点击内可达任意现存文档 |
| 1.3 | 发布写作规范与模板库 | documentation-system/ 全套文件（本目录） | 团队评审通过 |
| 1.4 | 存量文档登记造册 | 迁移登记表（spreadsheet 或 markdown）：207 篇文档逐一标注「保留迁移 / 归档 / 重写」 | 登记率 100% |
| 1.5 | imboyapp 根目录清理 | `TEST.md`、`TEST_1.md`、`QA_PRO_CLICK_TEST_REPORT.md` 等移入 `docs/qa/` 或归档 | 仓根只剩 README/DESIGN/CLAUDE/AGENTS |

**不做的事**：本阶段**不搬迁**任何存量文档内容，只建索引。避免大规模 git mv 引发的冲突与 review 疲劳。

## Phase 2 — 止血（第 3-5 周）

> 目标：补齐 P0 缺口，新人和部署者不再卡住。

| # | 任务 | 产出 | 验收标准 |
|---|------|------|---------|
| 2.1 | 教程：本地跑通后端 | `tutorials/quickstart-backend.md` | **一名未接触过本项目的工程师**按教程 15 分钟内跑通 `http://127.0.0.1:9800/api/v1/init` |
| 2.2 | 教程：私有化部署 | `tutorials/quickstart-deploy.md` | 按教程用 docker-compose.prod.yml 在干净机器部署成功 |
| 2.3 | 教程：SDK 第一条消息 | `imboy-sdk-js/docs/tutorials/first-message.md` | 教程代码复制即可运行 |
| 2.4 | API 参考自动生成 | Redoc 从 openapi.yaml 生成 `reference/api/` | openapi.yaml 与生成物 CI 强制同步 |
| 2.5 | WebSocket 协议参考 | `reference/websocket-protocol.md`：帧格式、ACK 重试、心跳、错误码 | 移动端 + 后端各一名工程师 sign-off |

**验收方式**：2.1/2.2 必须做「新手实测」——找没接触过的人，观察他按文档操作，卡住即文档 bug，修复后再测。

## Phase 3 — 流水线（第 6-8 周）

> 目标：文档质量门禁自动化，站点对外可访问。

| # | 任务 | 产出 | 验收标准 |
|---|------|------|---------|
| 3.1 | docs-site/ 脚手架 | VitePress 站点，本地可预览 | `bun run dev` 正常渲染全部 docs/ |
| 3.2 | CI：markdownlint + 死链 | docs.yml workflow | 坏格式 / 死链 PR 被拦截（先 warn 1 周过渡期） |
| 3.3 | CI：元信息头校验 | check-doc-meta.sh | 缺元信息的新文档 CI 红 |
| 3.4 | PR 模板加文档 checklist | 「文档已更新 / 无需更新」必选项 | 全仓库启用 |
| 3.5 | 站点上线 | nginx 反代部署（复用 deploy/ 栈） | 内网/公网 docs 域名可访问，搜索可用 |

## Phase 4 — 深化（持续，每季度排期）

> 目标：存量归位、解释型内容补齐、机制长效运转。

| # | 任务 | 说明 |
|---|------|------|
| 4.1 | 存量迁移 | 按 Phase 1 登记表逐批迁入四象限，每批 ≤ 20 篇，头部补元信息。目标两个季度完成 80% |
| 4.2 | 解释型文档 | 优先 5 篇：四层架构设计理由、E2EE 密钥轮换设计、TSID 选型、Garage S3 直传设计、插件系统隔离模型 |
| 4.3 | 插件开发指南 | imboy-plugin-marketplace/docs/plugin-development.md：从脚手架到上架全流程 |
| 4.4 | SDK 参考自动化 | TypeDoc 从源码注释生成 imboy-sdk-js API 参考，接入站点 |
| 4.5 | Vale 术语检查 | 统一术语表（TSID、E2EE、C2C/C2G…），CI 强制 |
| 4.6 | 文档健康度审计 | 每半年一次：准确性评分、过期归档、「最后验证」日期刷新 |

## 角色与投入估算

| 角色 | 职责 | 建议投入 |
|------|------|---------|
| 文档负责人（1 人） | 体系维护、模板与规范、Phase 协调、review | 50% 精力 × 8 周，之后 20% |
| 各模块 owner（后端/移动端/前端/运维各 1 人） | 本模块教程与参考的撰写、准确性 review | 每人每周 2-4 小时 |
| 工程负责人 | 治理机制背书、PR checklist 强制执行 | 例行评审即可 |

## 成功度量（上线后每季度统计）

- 新人 time-to-first-success（本地环境跑通）≤ 15 分钟
- 「文档找不到/看不懂」类内部提问量下降 50%
- CI 拦截的文档问题数（说明门禁在干活）
- 站点搜索无结果率 ≤ 20%
- 过期文档（「最后验证」超过 6 个月）占比 ≤ 10%
