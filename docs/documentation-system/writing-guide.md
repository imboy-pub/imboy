# IMBoy 文档写作规范

> **类型**：参考 · **读者**：所有文档作者 · **版本**：v1.0 · **最后更新**：2026-07-24

写文档前花 3 分钟读完本规范。Review 时按此验收。

---

## 1. 五条铁律

1. **代码示例必须能跑**。发布前在干净环境里亲自执行一遍。跑不通的示例比没有示例更糟糕。
2. **一篇文档只干一件事**。教程不塞参考表格，指南不讲设计哲学。想写第二类内容？拆出去，互相链接。
3. **不假设读者有上下文**。每篇文档要么自足，要么在开头明确链接前置阅读。
4. **文档随代码同版本**。PR 改行为，同 PR 改文档。过期文档标注归档，不删除。
5. **先写结构再写正文**。先列大纲（标题树），确认流向正确后再填内容。

## 2. 语言与语气

| 规则 | ✅ 正确 | ❌ 错误 |
|------|--------|--------|
| 第二人称、主动语态 | 「你运行 `make compile`」 | 「编译命令被用户执行」 |
| 现在时 | 「脚本创建 `.env` 文件」 | 「脚本将会创建 `.env` 文件」 |
| 结果先行 | 「完成本节后，你将拥有一个可收发消息的本地节点」 | 「本节介绍本地节点的相关内容」 |
| 具体描述失败 | 「若看到 `Error: econnrefused`，确认 PostgreSQL 已启动」 | 「如果出错，请检查配置」 |
| 诚实对待复杂度 | 「这一步有三个服务要协同，先看下面的时序图」 | 「这一步很简单」 |
| 中文为主，术语保留英文 | 「提交 PR 后等待 CI 通过」 | 「提交拉取请求后等待持续集成通过」 |

**删减原则**：一句话如果不能帮读者「做成一件事」或「理解一个概念」，删掉。

## 3. 结构规范

### 3.1 标题层级

- 每篇文档有且仅有一个 `#` 一级标题
- 层级不跳跃（`##` 之后是 `###`，不直接 `####`）
- 标题用动宾短语或名词短语，不用问句（FAQ 除外）

### 3.2 代码块

- 必须标注语言：` ```bash `、` ```erlang `、` ```dart `、` ```typescript `
- 命令与预期输出分成两个代码块：

````markdown
```bash
make ctl ARGS="node status"
```

预期输出：

```text
Node 'imboy@127.0.0.1' is running (uptime: 2h13m)
```
````

- 命令中不出现 `<占位符>` 风格，用全大写加下划线：`export IMBOY_DB_PASSWORD=你的密码` 或注释说明

### 3.3 表格与链接

- 配置项、参数、错误码一律用表格，不用段落罗列
- 跨仓引用文档时用完整描述（「见 imboyapp/docs/guides/build.md」），仓内引用用相对路径
- 外链到第三方（PostgreSQL 文档、Docker 文档）直接链官方最新版

## 4. 四类文档的写作要点

### 教程（Tutorial）
- 开头写明：你将做出什么、需要多久、前置条件清单（可勾选）
- 每一步：先说**做什么和为什么**，再给命令，再给**预期输出**
- 常见坑就地标注 `> **提示**：若遇到 X……`
- 结尾：回顾完成的事 + 「下一步」链接

### 操作指南（How-To）
- 标题是任务：「如何备份生产数据库」，不是「数据库备份介绍」
- 开头一句话说清适用场景与前提（「本指南适用于 Docker Compose 部署」）
- 步骤可跳读——每步自包含，不依赖「如上所述」
- 有回滚/降级方案必须写

### 参考（Reference）
- 只陈述事实，不教学、不劝诫
- 完整 > 精炼：参数全列、默认值全标、错误码全覆盖
- 每个 API 端点至少一个可运行的请求/响应示例

### 解释（Explanation）
- 讲「为什么」：背景、约束、被否决的替代方案
- 可以有观点，但标注权衡（「我们选择了 A 牺牲了 B，因为……」）
- 引用 ADR 编号，不复制 ADR 内容

## 5. 文件命名约定

| 规则 | 说明 | 示例 |
|------|------|------|
| 稳定文档用小写 kebab-case | 单词以连字符分隔，不用下划线/大写/中文 | `backup-restore.md`、`module-map.md` |
| 编号系列保持系列格式 | ADR、E2EE 规范等有序系列不拆散 | `adr/0001-four-layer-architecture.md`、`guides/e2ee/v2/` |
| 日期前缀只用于时效文档 | planning / archive / 一次性报告 | `planning/execution-checklist-2026-07.md` |
| 索引文件统一 `README.md` | 目录门户用大写 README；其余文档不用全大写文件名 | `docs/README.md` |
| 一次性产物完成后归 archive/ | 审计/评审/轮次台账不留活目录 | `archive/review/` |

## 5. Review 检查清单

文档 PR 的 reviewer 按此验收：

- [ ] 元信息头完整（类型 / 读者 / 适用版本 / 最后验证日期）
- [ ] 四象限归类正确，无混写
- [ ] 所有代码块标注语言，命令已在干净环境实测
- [ ] 无「简单」「很容易」「众所周知」等主观词
- [ ] 链接全部可达（CI 死链检查通过）
- [ ] 涉及的行为与当前代码版本一致（找对应工程师确认）
