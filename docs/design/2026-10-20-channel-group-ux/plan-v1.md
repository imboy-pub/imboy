### 1.2 总体判断

现有基础能力较多，最需完善的是**场景归属明确、列表状态独立、动作反馈可信、离开与返回可恢复**。应优先打通已有能力，不新增一套聊天/频道体系。

- **群组**是多人交流与协作主体，群聊是其中的交流行为；**频道**是发布与订阅主体，评论针对具体内容。
- **个人/企业是体验上下文**；资源的真实归属是 `personal` 或具体 `workspace`，创建后不可变。
- 企业壳里的工作区群聊、企业托管会话、客服会话有不同数据模型，不能只凭入口都在“企业”里就合并数据源。
- 组织是业务对象，不是租户。不能从该裁决推导“工作区/群成员校验可以取消”，也不能自动推导组织管理员拥有全部资源内容权限。
- 现有群详情已把公告/文件/相册、投票/日程/作业、其他设置分组，已有角色策略、草稿隔离与部分无障碍支持，继续复用。

权威解释：`docs/architecture/2026-10-12-organization-positioning-amendment.md` §1–3；`src/logic/group_logic.erl:788`、`src/logic/channel_logic.erl:374` 的不可变归属守卫。`docs/glossary.md`、`docs/concepts/collaboration-hierarchy.md` 与 App `CLAUDE.md` 的部分租户措辞仍过时，实施时应同步纠正这些权威文档，不能借本次 UX 改造扩大授权。

## 4. 目标信息架构与低保真交互

### 4.1 不增加一级导航，明确上下文

保持既有个人/企业切换、企业四栏结构与全局五项“+”菜单的既定方向。群/频道各有稳定列表入口，创建动作放到对应列表；消息页是快捷入口，同一资源复用详情。企业管理页保留治理操作，不承担普通成员的唯一建群入口。

```text
个人消息                          企业消息 · 企业名 / 工作区名
搜索会话                    +      搜索当前列表               +
频道更新  有新内容 >                消息 / 日程 / 待办
置顶会话                           全部 · 未读 · 群聊 · 频道
最近会话                           获授权的当前工作区消息

个人群组 / 频道目录                 工作区群组 / 频道目录
搜索                  创建          搜索                   创建
我的群 / 我管理                     已加入群 / 频道目录（明确名称）
列表/空态/错误                      创建仅对可创建的成员显示
```

“全部”当前实际是群消息集合，频道筛选会替换成目录，尚未统一为消息收件箱。短期说明其范围；中期若改为“全部交流”，只有得到各来源的授权摘要和排序契约后才能聚合。企业托管/客服会话继续使用各自入口；是否进入聚合列表属于 D1 待裁决。

个人消息顶端已有最多若干频道摘要，不能无限抢占聊天首屏。建议收成一条“频道更新”聚合入口或允许折叠，完整频道列表负责浏览；现有逐条摘要到聚合入口的变化列为建议，不能当成既定需求。

### 4.2 群组与频道创建

```text
创建群组                           创建频道
归属：企业名 / 工作区名（固定）      归属：个人 / 当前工作区（由入口固定）
群名称（工作区必填）                名称（必填）
选择成员 [搜索]                    简介、头像（可稍后补）
已选成员头像 + 人数                 访问：内部/公开/邀请（按场景约束）
成员列表 + 资格/不可选原因           高级设置：自定义 ID、标签、付费
                         创建      创建
```

1. 用户开始填写前即知道归属，提交前再在按钮附近显示；不提供创建后的“移动到企业”。换上下文先保留/放弃本草稿，不能静默改变资源归属。
2. 企业群只选 active 工作区成员；显示姓名与必要的部门/重名区分信息，不向普通用户要求粘贴 TSID。组织成员未加入该工作区时给出原因；加入/邀请是独立动作，不能建群时顺带授权。
3. 工作区 owner/member 的创建资格与 guest 限制由当前服务端裁决；组织角色、群角色、频道角色独立。源系统托管对象的不可修改项显示来源与管理去向。
4. 工作区频道固定显示“工作区内部”，与服务端内部化一致；不展示一个最终被服务端静默改为私有的“公开”选项。免费作为常规路径；付费现有能力按功能位展示，不在本任务删除，也不新增未约定收费流程。
5. 个人“发起聊天”目前选择一人也建群。建议名称明确为“发起群聊”；若要支持选一人直达单聊，采用独立“聊天/建群”意图，不能偷偷改变完成按钮含义。
6. 首屏只放名称/成员/归属等关键字段；头像、简介、标签等可稍后补。提交忙态防重，失败保留输入；超时结果未知时复用同一幂等键查询/重试，不能重新生成创建请求。
7. 创建完成直接进入群聊或频道；完善资料用非阻塞提示。工作区群“建成但改名失败”属于部分成功，继续处理同一个 gid。个人既有完成引导可保留，是否减少一次确认由 D4 决定。

### 4.3 频道阅读、发布、评论、讨论

```text
< 频道名称 · 工作区归属          分享  ⋯
简介（折叠）      已订阅 / 订阅 / 权益状态
置顶内容（最多展示一条摘要，更多可展开）
内容列表：标题/正文摘要、作者、时间、评论
有新内容 [查看]（阅读旧内容时）
进入讨论群「具体群名」 （仅合法绑定存在时）
发布者：[发布内容…]   读者：无聊天输入框
```

- 频道采用内容阅读心智，主标题只出现一次；发布者有明确“发布”动作，读者不出现可输入但发送必失败的聊天框。现有发布组件继续复用，不另造聊天流。
- 订阅前：公开个人频道展示策略允许的预览；邀请频道解释加入方式；付费频道区分订阅关系与购买权益。工作区目录可见不代表内容可读或可发布。
- 订阅中：忙态防重；订阅请求已成功但后续缓存刷新失败时说“已订阅，正在刷新”，重试对账而不是谎报订阅未发生。
- 评论围绕某条内容，页头保留内容摘要与返回定位；加入讨论群是另一件事。打开详情不自动加入群，绑定改变/失效要重新检查；绑定不存在时不造默认 General。
- 已加入的合法讨论群直接“进入讨论”；未加入但有资格显示“加入讨论群”并说明影响，确认后加入。现有 `ChannelDiscussionEntry` 已有显式确认与绑定复核，应扩展而不是替换。
- 默认保持当前内容排序；返回保留阅读位置。用户在读旧内容时新帖不抢滚动。列表与正文、详情搜索结果之间定位失败必须解释。
- 分享卡片/二维码只带可公开表达的标识，内容访问必须重新授权。跨空间链接不自动切全局工作区；保留现有 `ChannelLinkTargetPage` 的权威解析方向。
- 订阅、退订、免打扰、置顶分别反馈；退订不是退款，管理员身份不是购买凭据。付费/退款能力只在实际启用的交付档位验收。

### 4.4 群资料与协作

保留现有“群信息 → 成员 → 内容 → 协作 → 个人偏好 → 危险操作”分组。当前 `group_app_grid.dart` 已将入口转成分组行，不能再把旧“九宫格拥挤”当成现状缺陷。

- 头部显示群名、头像、人数和必要的工作区归属。群名、我在群里的昵称、仅自己可见的群备注分别标注影响对象。
- 成员预览有限个头像，“查看全部 N 人”有搜索/分页；添加/移除动作是操作，不用伪成员信息参与计数/搜索/读屏。
- 已加入群目录点行进聊天，点头像进群资料；未加入资源进入预览/申请，不能直接显示空聊天冒充已加入。
- 公告/文件/相册为内容；投票/日程/作业为协作；未启用功能隐藏入口，权限不足时按可解释性决定隐藏或只读。聊天里的协作卡片直达同一详情，并保留返回位置。
- 禁言显示原因与到期时间；不只置灰发送按钮。管理员能否管理某个成员按双方角色与服务端校验，不以“是管理员”放开全部操作。
- 归档、解散、移出工作区/群、托管来源限制各有状态文案；收到撤权后关闭可写组件并重新授权，不能停留在只会反复发送失败的页面。

## 5. 单聊、群聊与会话管理交互细则

### 5.1 消息状态与操作

| 状态/操作 | 用户应看到的反馈 | 约束 |
|---|---|---|
| 待发送/上传中 | 气泡/附件旁显示进度；可取消的操作才提供取消 | 不把本地入队写成已送达 |
| 服务端已受理 | 已发送；是否送达/已读由实际 ACK/回执决定 | 顺序继续使用 conv_seq，不按 ID 或客户端时间猜测 |
| 发送失败 | 气泡保留原内容，可点重试/更多；错误有可行动解释 | 同一消息重试沿用幂等身份；权限/禁言/资源失效不盲重试 |
| 引用 | 发送区显示被引用对象，可取消；点击引用定位或明确不可定位 | 不显示另一会话的消息；历史受权限/保留期/本机密钥限制 |
| 编辑/撤回 | 明确编辑态/已编辑/已撤回；失败保留原消息 | 沿用服务端时限；菜单可见性与真正执行能力目前不同，不直接合并既有策略 |
| 删除 | “从本机删除”与“撤回”明确分开 | 当前“为所有人删除”与撤回路径需要语义去重，不能承诺无限时全员删除 |
| 多选/转发 | 显示已选数量、目的地与发送确认；逐项失败可识别 | 未获授权的源内容不能因转发绕过访问；附件使用既有授权服务 |
| 历史/E2EE 不可用 | 说明当前原因与恢复入口；可恢复失败和无法恢复历史分开 | 不承诺服务端搜索密文或恢复没有备份/密钥的历史 |

长按菜单以复制/回复/转发等高频项优先，管理/删除归低频区；提供键盘/读屏可达的同等动作。不要用新增常驻按钮挤占每条气泡。现有动作已有较多实现，本阶段重点补状态与失败路径，避免重写。

### 5.2 会话列表

建议统一呈现优先级：名称与对象类型 → 时间 → 摘要 → 未读/通知状态。摘要依次表达草稿、@提醒、失败待处理、普通消息；多个状态并存时保留必要图标，不能把未读数字当任意待办容器。

- 置顶改变会话排序；免打扰改变通知；标未读/待处理改变个人提醒；三者独立。免打扰的未读样式与总徽标规则须统一，不能只改铃铛图标。
- 同一上下文刷新优先保留有效列表与滚动位置、显示轻量刷新状态；初始加载才使用整页骨架。过期授权快照不能无限保留；切账号/工作区时立即切走旧上下文。
- 移动端侧滑，桌面右键/更多，读屏自定义动作指向同一组能力；无后端状态就不显示“成功”的企业置顶/移除按钮。
- 会话名称/摘要搜索与消息全文搜索分开；搜索时明确范围。查询为空回原列表；无结果有“清除条件”；失败有重试。
- 未读按实际可见阅读推进；后台、路由遮挡和只是预加载不算已读。人工标已读是独立显式操作，必须处理失败与多端同步。
- 工作区消息继续以服务端授权快照为真源。可复用会话行视觉组件，但不复用个人数据 Provider 拼装企业内容。

### 5.3 离开和删除必须区分

| 动作 | 对会话/内容/关系的目标含义 | 必要提示 |
|---|---|---|
| 从列表移除 | 隐藏本人列表项，保留记录与成员/订阅关系 | 说明新消息是否重新出现及恢复入口；须先核实当前服务端软删除恢复行为 |
| 清空本机记录 | 清本设备可清除内容，保留关系；建议保持会话入口 | 明确是否可从服务端重新拉取，不能泛称“永久删除” |
| 退出群组 | 结束本人群成员关系；未来访问按重新加入规则 | 群名、历史影响、重新加入条件；群主先转让或显式解散 |
| 解散群组 | 群不再作为可用交流主体 | 独立高危确认，不能与普通“退出”共用模糊按钮 |
| 退订频道 | 结束订阅和对应更新提醒 | 不等于退款、不自动加入/退出其他资源；关联讨论资格按现行政策重验 |
| 归档资源 | 根据既有契约进入不可写/不可公开展示等状态 | 不把所有归档统称可恢复：工作区/频道和来源托管企业群的恢复能力不同 |

English: Message delivery, unread state and user reminders must remain distinct. Each destructive or relationship-changing action needs an accurate name, impact explanation and recoverable failure path.

## 6. 状态、权限和接口补齐

### 6.1 所有主页面的最小状态集合

| 状态 | 统一处理 |
|---|---|
| 首次加载 | 页面骨架/加载说明，保留返回动作 |
| 成功空 | 说明为什么为空；有资格时提供创建/加入/发现的一个主动作 |
| 搜索无结果 | 保留关键词，提供清除条件，不推荐跨范围资源来凑结果 |
| 刷新失败 | 同上下文仍有效的数据可保留，展示刷新失败/重试；不能把未验权限说成已验证 |
| 分页失败 | 原列表与游标保留，尾部重试，不替换整页、不重复插入 |
| 权限不足/已撤权 | 去除写入口，返回安全页面或显示权限说明；授权策略决定能否继续显示缓存 |
| 已归档/已解散/已删除 | 明确状态与合法后续动作；只有具备恢复能力和权限才展示恢复 |
| 提交结果未知/部分成功 | 说明哪些动作已完成，保留资源 ID/幂等键；后续恢复同一动作 |

### 6.2 权限展示原则

| 能力 | UI 判据 |
|---|---|
| 创建工作区群/频道 | 当前 active 工作区资格与可创建能力；guest 无创建入口，深链仍由服务端拒绝 |
| 读取工作区目录 | 目录读取资格；不得自动当作群成员/频道内容资格 |
| 群聊/群管理 | 实际群成员、成员状态、角色与来源策略；组织治理动作单独判定 |
| 频道发布/管理 | 频道编辑/管理员/创建者及服务端有效策略；订阅者不能发布 |
| 频道内容/讨论 | 工作区资格、订阅/邀请/购买、讨论绑定与群成员约束的组合 |
| 资源恢复/删除 | 独立治理能力，来源托管资源按现行合同处理 |

客户端的权限只决定呈现，服务端对每个动作重新授权。可以先复用现有角色策略；只有多处出现真实漂移时才补最小 capabilities 投影，不为 UX 新建通用 RBAC。

### 6.3 契约工作包（以下是目标增量，不是声称现有接口已支持）

1. **创建上下文**：App 创建参数透传 scope/workspace_id；工作区群名称和 request_id 的一次受理需检查并扩展现有 group/create 链，不新建平行建群 API。返回真实 gid、归属与动作结果。
2. **频道列表范围与分页**：subscribed/managed 返回 scope/workspace_id、授权后的订阅/角色/必要摘要；明确 personal/workspace 查询范围、稳定游标和查询条件绑定。保留旧客户端兼容，不只客户端过滤一页。
3. **工作区消息偏好**：补置顶/隐藏/待处理等确有需求的最小字段和 mutation；与现有消息快照资格、TTL、群成员世代绑定。免打扰若只本机生效必须标清；若需多端则扩展服务端契约。
4. **错误类型**：Channel API 保留业务错误类别与状态；加载/写入分别返回成功、拒绝、失败、结果未知；界面映射文案，不暴露堆栈/内部标识。
5. **历史定位**：先核实 conv_seq 历史接口能否安全拉到目标上下文；不足再设计 around-message 能力，不能无限从头拉历史；服务端密文与本机可搜索文本仍分开。
6. **查看/阅读游标**：频道与聊天分别定义语义，不共用一套“请求到即已读”。水位必须单调，撤回/过期/重加入世代要有明确行为。

## 9. 最小验收旅程

| 编号 | 条件与动作 | 必须看到的结果 |
|---|---|---|
| J01 | 企业工作区群列表 → 建群 → 选本工作区成员 → 提交 | 请求归属正确，进入同一群聊，个人域无误建资源 |
| J02 | 企业壳全局“发起聊天” | 在开始选择前明确其个人域语义；不暗示工作区建群 |
| J03 | 工作区 guest/无资格用户经按钮与深链尝试创建 | 界面解释限制，服务端拒绝；无半成资源 |
| J04 | 建群成功但改名失败/创建响应超时 → 重试 | 围绕原 gid/幂等身份恢复，不重复建群 |
| J05 | 创建个人频道、工作区频道 | 表单选项与真实可见范围一致，响应归属及回跳一致 |
| J06 | 订阅/管理 Tab 快切，反序完成请求，期间收到订阅事件 | 当前 Tab 只显示自身集合，滚动与查询条件不串 |
| J07 | A 频道 → B 频道 → 返回 A，A 请求晚返回，随后发布 | 标题、内容、评论、发布目标始终同一频道 |
| J08 | 登录切账号、切工作区、打开外部频道卡片 | 不残留旧上下文，不凭卡片自动切全局空间，不绕过权威授权 |
| J09 | 频道详情/消息请求分别返回 503、403、404 | 网络失败、拒绝、不可用与成功空可区分；不把失败当零内容 |
| J10 | 页面仍打开时撤销工作区/群/频道资格 | 内容与写入口按策略及时失效，返回/重启不能恢复无权操作 |
| J11 | 订阅已成功但回读失败 → 重试 | 说明已发生的订阅，完成对账；不误导再次购买/重复加入 |
| J12 | 有绑定/无绑定/绑定变更/已加入讨论群 | 有唯一准确讨论入口；不盲跳 General，不自动加入，不重复确认已加入 |
| J13 | 频道后台预加载/遮挡/前台阅读/阅读中来新帖 | 未读按所定查看语义推进，旧内容阅读位置不被抢走 |
| J14 | 工作区群/频道目录为空、搜索无结果、刷新失败 | 各自文案和下一步准确，刷新失败不显示成功空 |
| J15 | 个人 C2C 与 C2G 分别点头像、点整行 | 资料对象和聊天对象正确，返回原列表与位置 |
| J16 | 新会话还无消息时切免打扰；模拟本地写入失败 | 成功可回读；失败回滚且不提示成功；按定义核实另一设备行为 |
| J17 | 置顶、免打扰、标已读/待处理、移除，模拟服务端失败 | 各状态独立，失败不假成功，未读水位不倒退 |
| J18 | 发送/上传失败、重试、撤回、编辑、引用未加载旧消息 | 反馈准确、重试不重复、时限有效；不能定位有说明/合法恢复 |
| J19 | 群主离开、普通成员退出、清空本机、从列表移除 | 四种后果清楚，取消无副作用，返回栈和剩余权限正确 |
| J20 | 群/频道数超过一页，搜索尾页对象，翻页时新增/移除 | 不漏、不重、不无限转圈，查询范围真实；未支持规模需明确限制 |
| J21 | 已归档工作区/频道与来源托管群 | 正确只读/不可用，只有真实支持恢复的对象出现恢复动作 |
| J22 | 320/360 窄屏、横屏、键盘、大字、明暗、读屏/桌面键盘 | 主动作可达、无溢出/遮挡、焦点/标签清楚；独立记录真实平台证据 |

不采用“一个总 PASS”覆盖全部场景。每个旅程绑定候选 SHA、平台、交付配置、角色与结果；失败、未运行、跳过保留。历史测试通过或组件测试不能证明本轮产品已完备。

## 10. 实施前需要明确的产品选择

| 决策 | 推荐方向 | 取舍 |
|---|---|---|
| D1 企业消息“全部”的边界 | 本期只承诺当前工作区群消息与明确频道更新入口；托管/客服继续独立；未来有授权投影再聚合 | 清楚可用，减少三个会话实体混写；若要统一收件箱，必须增加来源、能力与排序契约 |
| D2 个人频道列表范围 | personal 专属；跨空间资源由明确链接/企业入口访问 | 归属易懂；若需“我的全部订阅”，单独命名并显示工作区来源，不暗中混入 |
| D3 频道已读语义 | “已查看新内容”，按前台可见内容推进，不宣称读完全文 | 未读更可信；若采“进入即清零”，必须显式称查看而非阅读完成，并处理页内新帖 |
| D4 建群与清理交互 | 明确“群聊”意图，创建后直达；清空保持入口、移除只隐藏、群主优先转让后退出 | 少一步且后果明确；需确认与既有创建引导、软删除恢复策略的兼容性 |

本轮建议优先批准 S1 的状态/反馈修复与 S2 的工作区创建、目录闭环；其余先明确 D1–D4，再逐步扩展契约。本文未授权 commit、push、合并、部署、生产迁移或影响第三方的实际操作。
