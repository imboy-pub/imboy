# ImBoy APP 平滑升级降级方案

> 目标：让用户无感知地完成版本升级，遇到问题能安全回退，不丢数据。

---

## 一、整体思路（一句话版）

```
服务端控制"谁该升级、升到哪个版本" → 客户端执行"下载安装 + 本地数据库迁移" → 出问题就回滚
```

---

## 二、当前已有的能力

| 能力 | 现状 | 评价 |
|------|------|------|
| 服务端版本查询 API | ✅ 客户端传版本号，返回最新版本 | 够用，需扩展 |
| 管理后台版本管理 | ✅ 增删改查 + 按地区/平台分管 | 够用，需扩展 |
| 客户端下载安装 | ✅ Android APK下载安装 + iOS跳AppStore | 够用 |
| SQLite 本地数据库迁移 | ✅ 升级/降级SQL脚本 + 快照备份 + 完整性校验 | **做得很好** |
| 强制更新标记 | ✅ force_update 字段 | 太粗糙，需细化 |

**结论：基础框架已有，缺的是"策略控制"和"安全保障"。**

## 三、方案设计

### 3.1 升级策略：三级升级制

行业标准做法（微信、钉钉、飞书都是这个思路）：

```
┌─────────────────────────────────────────────────────┐
│                    三级升级策略                        │
├──────────┬──────────────┬───────────────────────────┤
│  级别     │  用户体验     │  什么时候用                 │
├──────────┼──────────────┼───────────────────────────┤
│ 强制升级  │ 全屏弹窗      │ 安全漏洞、协议不兼容         │
│          │ 不能关闭       │ 必须升级才能继续用           │
│          │ 不能跳过       │                           │
├──────────┼──────────────┼───────────────────────────┤
│ 推荐升级  │ 弹窗提醒      │ 重要新功能、性能优化         │
│          │ 可以关闭       │ 建议升级但不强制             │
│          │ 下次启动再提醒  │                           │
├──────────┼──────────────┼───────────────────────────┤
│ 静默提示  │ 设置页小红点   │ 小修小补、界面调整           │
│          │ 不弹窗        │ 用户想升就升                │
│          │ 不打扰        │                           │
└──────────┴──────────────┴───────────────────────────┘
```

**判断逻辑（服务端决定）：**

```
用户当前版本 < 最低支持版本？  → 强制升级
用户当前版本 < 最新版本 且 标记为强制？ → 强制升级
用户当前版本 < 最新版本 且 标记为推荐？ → 推荐升级
用户当前版本 < 最新版本？ → 静默提示
用户当前版本 = 最新版本？ → 不处理
```

### 3.2 最低支持版本（关键安全网）

**这是整个方案最重要的概念。**

```
举例说明：

当前最新版本：2.0.0
最低支持版本：1.5.0（你在后台配置的）

用户A（版本 1.8.0）→ 高于 1.5.0 → 推荐升级，不强制
用户B（版本 1.3.0）→ 低于 1.5.0 → 强制升级，不升级不让用
用户C（版本 2.0.0）→ 等于最新   → 啥也不做
```

**为什么需要？**
- 旧版本可能有安全漏洞
- 旧版本可能和新的服务端协议不兼容
- 保证线上运行的客户端都在可控范围内

### 3.3 灰度发布（降低风险的关键手段）

**不要一次把新版本推给所有人。** 行业标准做法：

```
第1天：推给 5%  的用户 → 观察崩溃率、用户反馈
第3天：推给 20% 的用户 → 继续观察
第5天：推给 50% 的用户 → 基本稳定
第7天：推给 100% 全量发布
```

**怎么决定谁在 5% 里面？**

用设备ID（did）做哈希取模，简单可靠：

```
hash(did) % 100 < 灰度比例 → 命中灰度，推送新版本
hash(did) % 100 >= 灰度比例 → 未命中，暂时不推
```

这样每个用户的结果是固定的（同一个设备要么一直命中，要么一直不命中），避免时推时不推的混乱。

### 3.4 数据库升降级（已有，需加固）

当前 MigrationService 已经做得不错，需要加固的点：

```
升级流程（当前 ✅ 已有）：
  ① 创建快照备份
  ② 开始事务
  ③ 逐版本执行升级 SQL
  ④ 校验数据完整性（PRAGMA integrity_check）
  ⑤ 提交事务
  ⑥ 如果失败 → 回滚事务 → 从快照恢复

需要加固的点（⬆ 新增）：
  ⬆ 保留最近3个版本的快照（现在只保留最新的）
  ⬆ 迁移过程中显示进度条（避免用户以为卡死了）
  ⬆ 迁移失败时给用户明确的提示和"重试"按钮
  ⬆ 记录迁移日志（方便排查问题）
```

### 3.5 WebSocket 版本保护

当前 WebSocket 握手传了 `vsn` 但没做检查。增加：

```
客户端连接 WebSocket
     │
     ▼
服务端读取 vsn header
     │
     ▼
版本 < 最低支持版本？──是──→ 发送 S2C "app_upgrade" 消息（force=true）
     │                      连接保持，但提醒用户升级
     否
     │
     ▼
正常处理消息
```

**注意：不要直接断开连接，而是发消息提醒。** 这样用户至少能收到消息通知，体验更好。

## 四、数据库变更

### 4.1 扩展 app_version 表

在现有表上增加字段（不影响已有数据）：

```sql
-- 最低支持版本：低于此版本的客户端被强制升级
ALTER TABLE app_version
  ADD COLUMN min_supported_vsn varchar(40) DEFAULT '0.0.0';

-- 灰度比例：0-100，100 表示全量发布
ALTER TABLE app_version
  ADD COLUMN grayscale_percent smallint DEFAULT 100;

-- 升级类型：force=强制 / recommend=推荐 / silent=静默
-- 替代原来的 force_update 字段，更灵活
ALTER TABLE app_version
  ADD COLUMN upgrade_type varchar(20) DEFAULT 'recommend';

-- 更新日志：JSON 数组，结构化展示
-- 例: [{"tag":"新功能","text":"支持频道"},{"tag":"修复","text":"消息偶尔丢失"}]
ALTER TABLE app_version
  ADD COLUMN changelog jsonb DEFAULT '[]';

-- 安装包大小（字节），展示给用户看
ALTER TABLE app_version
  ADD COLUMN file_size bigint DEFAULT 0;

-- 安装包 SHA256 校验值，下载完验证是否完整
ALTER TABLE app_version
  ADD COLUMN file_hash varchar(128) DEFAULT '';
```

**兼容性：** 全部是新增字段且有默认值，不影响现有逻辑。

### 4.2 新增版本策略配置表

```sql
-- 全局版本策略（每个平台一条记录）
CREATE TABLE IF NOT EXISTS app_version_policy (
  id         bigint PRIMARY KEY,
  type       varchar(20) NOT NULL,          -- android / ios
  -- 全局最低版本（管理员手动设置，兜底安全网）
  min_vsn    varchar(40) DEFAULT '0.0.0',
  -- 是否启用灰度（0=关闭直接全量，1=启用）
  grayscale_enabled smallint DEFAULT 0,
  -- 版本检查间隔（小时），客户端按此频率检查
  check_interval_hours int DEFAULT 24,
  status     smallint DEFAULT 1,
  updated_at timestamptz DEFAULT now(),
  created_at timestamptz DEFAULT now(),
  UNIQUE(type)
);
```

## 五、API 变更

### 5.1 版本检查 API（改造现有）

**请求（不变）：**
```
GET /app_version/check?vsn=1.2.0&region_code=cn
Header: cos=android, did=device-abc-123
```

**响应（扩展）：**
```json
{
  "vsn": "2.0.0",
  "download_url": "https://...",
  "updatable": true,

  "upgrade_type": "recommend",
  "min_supported_vsn": "1.5.0",
  "changelog": [
    {"tag": "新功能", "text": "支持频道聊天"},
    {"tag": "优化", "text": "消息加载速度提升50%"},
    {"tag": "修复", "text": "偶尔消息发送失败"}
  ],
  "file_size": 45678901,
  "file_hash": "sha256:abcdef...",
  "check_interval_hours": 24
}
```

**向后兼容：** 旧客户端只认 `updatable` + `force_update`，新字段忽略即可。

### 5.2 服务端判断逻辑

```
输入：客户端版本(client_vsn)、设备ID(did)、平台(cos)、地区(region)

第1步：查全局策略表 → 拿到 min_vsn
第2步：查最新版本 → 拿到 latest_vsn + grayscale_percent + upgrade_type
第3步：判断

  if client_vsn < min_vsn:
      return upgrade_type = "force"  -- 低于底线，强制升
      
  if client_vsn >= latest_vsn:
      return upgrade_type = "none"   -- 已是最新，不处理
      
  if grayscale_percent < 100:
      if hash(did) % 100 >= grayscale_percent:
          return upgrade_type = "none"  -- 未命中灰度，暂不推
          
  return 版本记录中配置的 upgrade_type  -- force / recommend / silent
```

## 六、客户端变更

### 6.1 版本检查时机

```
┌─────────────────────────────────────────────┐
│              版本检查时机                      │
├──────────────┬──────────────────────────────┤
│ APP 启动      │ 延迟 3 秒后检查（不阻塞启动）   │
│ 定时检查      │ 每 24 小时检查一次              │
│              │ （间隔从服务端获取，可动态调整）   │
│ 服务端推送    │ 收到 S2C app_upgrade 消息      │
│              │ 管理员发布新版时主动推送          │
│ 手动检查      │ 设置页 → 检查更新按钮           │
└──────────────┴──────────────────────────────┘
```

### 6.2 升级 UI 行为

```
upgrade_type = "force"
  → 全屏弹窗，没有关闭按钮
  → 只有"立即更新"按钮
  → 按返回键无效
  → 不升级就不能用APP

upgrade_type = "recommend"
  → 弹窗，有关闭按钮
  → "立即更新" + "稍后提醒"
  → 关闭后下次启动APP再提醒（24小时内不重复弹）

upgrade_type = "silent"
  → 不弹窗
  → 设置页"关于"里显示小红点
  → 用户主动点进去才看到更新

upgrade_type = "none"
  → 完全不处理
```

### 6.3 下载安全增强

```
下载完成
   │
   ▼
计算文件 SHA256
   │
   ▼
与服务端返回的 file_hash 比较
   │
   ├─ 一致 → 安装
   │
   └─ 不一致 → 提示"下载文件损坏，请重试"
              → 删除损坏文件
              → 自动重新下载（最多重试2次）
```

## 七、降级场景处理

### 什么时候会降级？

```
场景1：新版本有严重 bug → 用户手动安装旧版 APK
场景2：应用商店审核不过 → 紧急下架新版，用户重装回旧版
场景3：管理员把最低版本调低 → 允许用户继续使用旧版
```

### 降级时数据怎么处理？

```
用户安装旧版 APP（版本 1.8.0，数据库 v10）
当前本地数据库已经是 v13
     │
     ▼
SQLite onDowngrade 触发
     │
     ▼
MigrationService 执行降级：
  ① 创建当前数据库快照（v13 的完整备份）
  ② 开始事务
  ③ 执行 downgrade.sql 中 v13→v12→v11→v10 的脚本
  ④ 校验数据完整性
  ⑤ 成功 → 提交，APP 正常运行
     失败 → 回滚，从快照恢复 v13
           → 提示用户"数据恢复失败，请升级到最新版本"
```

**重要原则：降级可能丢失新版本新增的数据字段，但绝不能让APP崩溃或无法启动。**

## 八、实施顺序（分 3 期）

### 第 1 期：核心安全网（建议先做）

```
耗时预估：3-5 天

做什么：
  ✅ 数据库加字段（min_supported_vsn、upgrade_type、changelog 等）
  ✅ 新建版本策略表（app_version_policy）
  ✅ 改造版本检查 API（返回 upgrade_type）
  ✅ 客户端解析新字段 + 三级升级 UI

效果：
  管理员能控制"最低版本"和"升级方式"
  客户端能区分强制/推荐/静默三种升级
```

### 第 2 期：灰度发布 + 安全增强

```
耗时预估：2-3 天

做什么：
  ✅ 灰度发布逻辑（基于 did 哈希取模）
  ✅ 管理后台灰度比例配置
  ✅ 下载文件 SHA256 校验
  ✅ WebSocket 版本保护（发 S2C 升级提醒）

效果：
  新版本可以分批推送，降低风险
  下载的安装包有完整性校验
```

### 第 3 期：可观测性

```
耗时预估：1-2 天

做什么：
  ✅ 客户端版本分布统计
  ✅ 管理后台版本统计面板
  ✅ 升级事件日志
  ✅ 数据库迁移加固（保留3个快照、进度条、重试）

效果：
  管理员能看到各版本用户占比
  出问题时有日志可查
```

## 九、安全兜底策略

```
┌────────────────────────────────────────────────────────┐
│                      安全兜底层级                        │
│                                                        │
│  第1层：灰度发布                                         │
│    → 新版本先推 5% 用户，有问题影响面小                     │
│                                                        │
│  第2层：最低版本控制                                      │
│    → 管理员随时可以把最低版本调高，强制旧版本升级             │
│    → 也可以调低，允许用户暂时用旧版本                       │
│                                                        │
│  第3层：SQLite 快照备份                                  │
│    → 每次数据库迁移前自动备份                              │
│    → 迁移失败自动回滚到备份                                │
│                                                        │
│  第4层：WebSocket 版本提醒                               │
│    → 即使用户忽略了弹窗，连接WS时也会收到升级提醒            │
│                                                        │
│  第5层：管理员紧急操作                                    │
│    → 管理员可以随时禁用某个版本（status=0）                 │
│    → 管理员可以推送 S2C 消息强制所有在线用户检查更新         │
│                                                        │
│  最后兜底：客户端本地缓存                                  │
│    → API 不可用时，用上次的检查结果                         │
│    → 不会因为服务端故障导致APP无法使用                      │
└────────────────────────────────────────────────────────┘
```

## 十、一个完整的升级流程示例

```
管理员在后台发布 2.0.0 版本：
  - upgrade_type = recommend（推荐升级）
  - min_supported_vsn = 1.5.0
  - grayscale_percent = 10（先推 10%）
  - changelog = [{"tag":"新功能","text":"频道聊天"},...]

=== 用户小明（版本 1.8.0，did=abc123）===

1. 小明打开APP
2. 3秒后，客户端请求 /app_version/check?vsn=1.8.0
3. 服务端计算：
   - 1.8.0 >= 1.5.0（不需要强制）
   - 1.8.0 < 2.0.0（有新版本）
   - hash("abc123") % 100 = 42 → 42 >= 10 → 未命中灰度
   - 返回 upgrade_type = "none"
4. 小明什么提示都没看到 ✓

=== 第二天，管理员把灰度调到 50% ===

5. 小明打开APP
6. hash("abc123") % 100 = 42 → 42 < 50 → 命中灰度！
7. 返回 upgrade_type = "recommend"
8. 小明看到弹窗："有新版本 2.0.0 可用"
   - 显示更新内容列表
   - "立即更新" / "稍后提醒"
9. 小明点"立即更新"
10. 下载 APK → 校验 SHA256 → 安装
11. APP重启，SQLite 从 v13 升级到 v15
    - 创建快照
    - 执行升级SQL
    - 校验完整性
    - 完成！
12. 小明正常使用 2.0.0 ✓

=== 如果 2.0.0 有严重bug ===

13. 管理员把 2.0.0 的 status 设为 0（禁用）
14. 管理员发布 2.0.1 修复版
15. 管理员设 upgrade_type = "force"
16. 所有 2.0.0 用户下次检查时会被强制升级到 2.0.1 ✓
```
