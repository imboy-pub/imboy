## 3. E2EE-062 实际做到了什么（12 刀）

按"防御链"顺序，而非发现顺序：

| 环节 | 结果 |
|---|---|
| 幂等租约（单设备 / batch） | 同 request_id 重放只消费一条 OTK；真 PG 100 次重放 + 50 路并发实证 |
| 目标级限流 | 键从"领取方"改为"**被领取方**"，堵住"换账号/换 request_id"抽干同一目标 |
| 配置漂移可见 | 未注册 scope 返回 `rate_not_set` 会**静默关掉限流**；已收敛为唯一判定点并打 ERROR；`sys.config` 里的两个 scope 已被测试钉死 |
| 客户端幂等键 | 服务端能力此前在生产流量上**等于零**，现已接线 |
| 余量查询 + 低水位补传 | 新端点（查询对象只取自 token，不接受入参）；客户端 `countPrekeys` 从恒 0 桩实现改为真实查询 |
| 耗尽可观测 | `olm_otk_exhausted_total` / `olm_prekey_unavailable_total`，**不带 uid**（"谁的池快空了"正是攻击择时信号）；已实证确实出现在 `/metrics` 输出 |
| 绝不降级明文 | 发现并修复：`MessageRetry` 绕过 `encryptPayload` 与 PolicyGate **按库中原样重发明文**；闸门前移到 CAS 之前；C2C 与 C2G 两支均实证 |
| fallback 验签 | 服务端可验（两阶段第一阶段）；客户端两个调用点均签名；空签名现已 fail-closed 拒发 |
| fallback 轮换 | 从"仅登录时"改为周期轮换（触发点挂入站建会话后，因为"长期不登录"正是缺口成因）；`forgetFallbackKey` 经特征化后**裁决不调用** |

### 3.1 过程中被实证推翻的假设（值得记住的部分）

- `process: true` 会触发服务端处理 → **只是上传进度 UI**；
- presigned URL 的签名覆盖 Content-Type 请求头 → **只签 host**，MIME 是以 query 参数进签名；**且求证对象原本就找错了**（权威是我方 `elib_s3_sign`，不是 Garage）；
- vodozemac 文档 "forget the **current** fallback key" → **实际丢的是上一把**（上游文档错误）；
- 我自己写的 `seed: true  // 首次注册` → 该注释对那个调用点是错的，**每次登录都会跑**，导致健康的 OTK 池被反复全量重建。

## 4. E2EE-062 残留（按解除条件分组，不按发现顺序）

| 解除条件 | 残留项 |
|---|---|
| **需部署侧配置 + 基线数据 + promtool** | 耗尽告警规则（"运维不再盲"的最后一段） |
| **需联调 / 起服务 / 真机** | 幂等与补传链路端到端；nginx `/metrics` 403 实跑；60/min 阈值压测；真机双端 |
| **需等外部条件** | 服务端 fallback 签名改必填（等 `olm_fallback_unsigned_total` 归零）；单租户/全局限流（有意识缺口，应由网关承担） |
| **有意识的设计结果，非缺陷** | fallback key 留存期 ≈2 个轮换周期；完全不收消息的设备不轮换；进程重启后重投消费新 OTK；`forgetFallbackKey` 不调用 |
| **已界定为低价值** | `report_identity` 服务端验签（对端客户端已在验，且攻击者可自造一致三元组） |
