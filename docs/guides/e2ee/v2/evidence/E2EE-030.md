## 3. 根因与修复

**根因**：`OlmSessionService` 把 ratchet 状态**双写**到事务性 `CryptoStore`（SQLCipher）与
`FlutterSecureStorage`，而 `_loadSession` 固定优先读 CryptoStore。任一侧漏写即产生两份分叉状态：
DB 短暂不可用期间 ratchet 只推进到 SecureStorage，进程重启后从 DB 读回**陈旧** pickle → ratchet 回滚
→ 已消费的 message key 被重用 → 前向保密失效（对端亦无法解密）。

**修复**（`lib/service/olm_session_service.dart`、`lib/service/e2ee/crypto_store.dart`）：

1. 事务存储成为 ratchet 状态的**唯一权威副本**，删除 3 处 SecureStorage 双写
   （`_persistSession`、`encryptC2CMessage` outbox 分支、`_persistSessionWithDedupe`）。
2. 新增 `OlmStateCommitException`；新增共享守卫 `_requireStore()`：CryptoStore 不可用时
   **驱逐内存会话副本并 fail-closed 抛错**，绝不退化到非事务存储。驱逐是必需的——
   `session.encrypt/decrypt` 就地推进内存 ratchet，保留内存副本会造成"内存已推进、磁盘未推进"的分叉。
3. `_loadSession` 对 legacy SecureStorage pickle 改为**一次性只读导入**：写入 CryptoStore 后立即
   删除明面副本，消除双副本分叉类。升级不丢会话。
4. `CryptoStore.deleteAllSessions()` + `clearAll()` 显式清理：ratchet 状态离开 SecureStorage 后，
   `E2eeSecretInventory` 的 `olm_` 前缀擦除不再覆盖它，登出必须显式清（防 E2EE-015 回归）。

Account pickle 与 pickle 主钥仍留在 Keychain/Keystore（ADR 07 分级不变）。

   才能检测，评估后判定为过度设计，留待 E2EE-051 crash-consistency 一并权衡）。
