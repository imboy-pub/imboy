## 1. 做了什么

周期轮换那一刀把「`forgetFallbackKey()` 从未被调用」列为残留，但**没有调它**——
理由是语义不清：Dart 侧文档写 "Forget the **current** fallback key"，
与 vodozemac Rust 侧的常见描述（丢弃**上一把**）矛盾，而**误调会丢在途消息**。

本刀用真 vodozemac 把语义与留存期一次性钉死。
新增 `test/service/e2ee/fallback_forget_characterization_test.dart`（4 例，全绿）。

---

## 2. 实证结果

### 2.1 ⚠️ Dart 文档是错的

| 场景 | 实测 |
|---|---|
| **对照组**：全新账号（无 fallback key）→ forget | 返回 `false`。它红就说明我对该 API 的基本理解不对，后面几条都不必看 |
| 只有一把（从未轮换）→ forget | 返回 `false`，且**该 key 仍可解密** |
| 轮换过一次 → forget | 返回 `true`；**上一把**不可解密，**当前那把仍可解密** |

**结论：丢的是上一把（previous），当前那把保留。**
若 Dart 文档属实（"forget the current"），第二条应当解不开——实测解得开。
**这是又一个「静态阅读只能形成假设」的实例：这次错的不是我的推理，是上游文档。**

### 2.2 决定性发现：**轮换本身就会挤掉"上上把"**

第四条用例连续轮换三次：

```
轮换 k1 → k2：k1、k2 均可解密（previous + current）
再轮换 k3   ：k1 已**不可解密**，k2、k3 可解密
```

即 vodozemac 最多保留 **current + previous** 两把。
**每把 key 的留存期已经被轮换周期自然界定在约两个周期内**
（作为 current 一个周期 + 作为 previous 一个周期；本项目 7 天周期 ⇒ 约 14 天）。

---

## 3. 裁决：**不调用 `forgetFallbackKey()`**

显式调用能把留存期从约 2 个周期缩短到约 1 个周期。收益与代价：

| | 内容 |
|---|---|
| **收益** | 旧私钥少留存约 7 天 |
| **代价** | 刚被替换的那把 key 立即失效。对端可能在几分钟前才 claim 到它、消息正在路上——**这些消息会解不开**（§2.1 第三条已实证该机制） |

留存期本就有界（§2.2），不是"无限期"那类问题；而丢消息是**用户可见的功能损坏**。
按「两种合理实现选安全那个」，**不调用**。

**因此上一刀的残留 1 应从"待办"改判为"已裁决：不调用"。**
若将来要调，安全的时机是「确信旧 key 上不会再有在途消息之后」，
而那个判断需要的信息（对端何时 claim 过该 key）**服务端有、客户端没有**——
真要做，应当是服务端驱动的，不是客户端自行决定。

## 6. 残留风险（E2EE-062 仍未完成）

1. ~~`forgetFallbackKey()` 未调用~~ → **已裁决关闭**（§3）。
2. **fallback key 留存期约 2 个轮换周期（≈14 天）** —— 这是接受的设计结果，
   不是缺陷；但若将来把周期从 7 天调大，留存期会同比放大。
   **认识论状态：留存上界已实证；"14 天是否可接受"未针对威胁模型论证。**

6. 告警规则未做；`/metrics` 输出未实证；
7. 被拦下的重发行仍被扫描器每轮捡起（不写库、不出网）；滞留后 UX 无具体提示；
8. 幂等/补传链路端到端未实证；单租户/全局限流未做；租约无独立 TTL；
   60/min 未压测；进程重启后重投仍消费新 OTK；客户端无 batch_claim 调用方；
