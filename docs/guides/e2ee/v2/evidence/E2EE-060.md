## 1. 契约来源

ADR 15 §10「实现落点 · Erlang (`imboy`)」：

> - 仍不解密、不解析业务 payload。
> - 只做外层尺寸、必填字段类型、版本、速率限制和原样透传；不得重建/裁剪 `protected_header`。
> - WS/HTTP 两条路径必须 byte/semantic preserving，并有契约测试。

## 2. 发现的缺陷（本任务实测，非推断）

### 2.1 P0 —— protobuf 出站编码静默裁剪整个 PFv3 信封

`proto/imboy.proto` 的 `message E2EEMeta`（§128）只定义了
`ver / suite / nonce / keys / protocol / protocol_version / peer_uid /
peer_device_id / message_type / session_id / message_index / group_id /
meta_version` 十三个字段。

PFv3 的外层信封字段 —— `protected_header`、`header_hash`、`ciphertext`、
`protocol_metadata`，以及 E2EE-029 per-device fan-out 的 `fan_out`、`devices`
—— **在 schema 中完全没有落点**。

`src/lib/imboy_codec.erl` 的 `e2ee_to_pb/1` + `e2ee_to_pb_ext/2` 逐字段白名单
搬运，其余字段一律丢弃且**不报错**。生产链路：

```
imboy.v2 子协议 → negotiate_protocol → {protobuf, v2}
  → websocket_handler:ws_reply(protobuf, v2, Msg)
  → imboy_codec:encode(protobuf, Msg) → to_pb_map → e2ee_to_pb
  → 信封被裁掉，只剩 meta_version=3 + protocol=olm
```

接收端拿到 `meta_version=3` 却没有 `protected_header`/`ciphertext`，
**该消息永久不可解密**——服务端不持有密钥，事后无法补救。

**影响范围（已核实，未夸大）**：C2C/C2G 的**投递（fan-out）**路径走的是
`encode_delivery_frame_v2/1`，该函数出于历史原因（protobuf `bytes payload`
被 protobuf-dart 暴露成 base64 字符串，见其函数内注释）已经把 v2 帧 payload
固定为 JSON 原文，因此**投递路径未受影响**。受影响的是：

1. `ws_reply/3` 的**同步响应**路径（`websocket_handler.erl:544`、`:286`）——
   任何携带 e2ee 的同步回帧；
2. `imboy-protobuf` 子协议（`framing=none`）连接的全部出站消息；
3. `encode_delivery_frame_protobuf/1`（`{protobuf, none}` 组合）。

即：不是当前默认 Flutter 客户端的主投递路径，但是一条**真实可达且静默**的
数据毁损路径，且随任何一次"把同步响应也走 protobuf"的改动即刻扩大。

### 2.2 P1 —— 入站无外层信封校验

`message_ds:validate_message/1` 对 `e2ee` 字段零校验。畸形的 v3 信封
（缺 `protected_header` / 缺 `ciphertext` / 字段类型错误 / `devices` 空）
可以直接进入 staging 落库并向全部在线设备广播。

同样没有尺寸上界：cowboy 的 `max_frame_size => 2097152` 是唯一约束，
而它的效果是**断开连接（1009）**，不是"稳定错误"，也不覆盖非 WS 入口。

## 4. 修复

### 4.1 `src/lib/imboy_codec.erl` —— fail-closed，不产出裁剪结果

- 新增 `?E2EE_PB_FIELDS` / `?E2EE_PB_KEY_FIELDS` 两个白名单常量，
  与 `e2ee_to_pb/1`、`e2ee_from_pb/1` 的读写字段一一对应。
- 新增导出 `e2ee_pb_lossless/1`：e2ee map（含 `keys` 列表元素）出现任何
  E2EEMeta 没有的字段，即判为不可无损表达。**白名单而非黑名单**，
  所以 PFv3 字段与一切未来扩展字段自动被覆盖，不需要随协议演进逐个补判断。
- `encode(protobuf, Msg)` 在不可无损时**拒绝编码返回 `<<>>`**，并只记录
  消息 id（不记录任何信封内容）。`<<>>` 是该函数既有的错误返回约定，
  调用方 `encode_delivery_frame_protobuf/1` 早已对其做 JSON 回退。
- 新增导出 `encode_ws_msg/4`：把"按协议/framing 选择线上编码"的决策下沉到
  codec。不可无损时退回 byte-preserving 的 JSON；v2 framing 仍做 `wrap_v2_frame`
  包裹，与 `encode_delivery_frame_v2/1` 既有做法一致。

### 4.2 `src/api/websocket_handler.erl` —— `ws_reply/3` 委托给 codec

两个子句合并为一行委托。对所有**可达**的 `{Protocol, Framing}` 组合，
非 e2ee 消息的编码结果与修复前逐字节相同（`negotiate_protocol/1` 只产出
`{protobuf, v2}`、`{protobuf, none}`、`{json, none}` 三种组合，
`{json, v2}` 不可达）。

### 4.3 `src/ds/message_ds.erl` —— 入站外层信封校验

新增 `validate_e2ee_envelope/1`，接在 C2C/C2G/C2S 的 `validate_message_by_type`
末尾，即 staging 落库与广播**之前**：

1. **尺寸上界**：默认 1 MiB，`application:get_env(imboy, e2ee_envelope_max_bytes, 1048576)`
   可覆盖。取 1 MiB 的理由：远大于任何合法信封（PFv3 header 客户端硬上限 8 KiB，
   C2C fan-out 只针对对端少数几台设备），又**低于 cowboy 的 2 MiB `max_frame_size`**,
   保证超限时先返回稳定业务错误 `e2ee_envelope_too_large` 而不是断连。
2. **`meta_version >= 3` 时的必填字段**：支持 ADR 15 §3.3 单信封与 E2EE-029
   per-device fan-out 两种形态；`protected_header` / `header_hash` / `ciphertext`
   必须存在且为非空 binary。
3. **只查存在性与类型，不解析内容**：不做 base64 解码、不做 CBOR 解析、
   不重建 canonical header。未知扩展字段一律放行（前向兼容，已有护栏测试）。

## 7. 残留风险

1. **「未知 critical version 按契约拒绝」未实现**。当前对 `meta_version >= 3`
   统一按 v3 形态校验：未来的 v4 若沿用同样的外层三字段则被放行、否则被拒。
   ADR 15 未定义 critical/non-critical version 的判定规则，也未定义
   version negotiation 的拒绝语义，**属协议缺口而非实现缺口**，
   自行发明会越过 ADR 冻结边界（执行规则 13）。建议并入 ADR 14–19 签字批次处理。
2. **HTTP 入口未覆盖**。`21` 的范围写了「HTTP/WS handler」，但当前后端不存在
   接收 e2ee 消息的 HTTP 端点（消息一律经 WS）。本任务因此只覆盖 WS + DB。
   若将来新增 HTTP 发消息端点，必须复用 `message_ds:validate_message/1`
   才能继承本次校验。
3. **速率边界未新增**。`21` 提到「速率边界」；现有 `websocket_handler` 已有
   限流（`:286` 的 `RateLimitMsg`），本任务未评估其是否足以覆盖 E2EE 场景。
   建议随 E2EE-062（OTK 抗耗尽）一并复核。
4. **`v2_frame_e2e_tests` 2 项预存失败未修**。已确认与本任务无关（基线同样失败），
   但它们位于 v2 framing 的错误处理路径上，建议单独立项。
5. **1 MiB 上界的可用性风险**。若未来 C2C fan-out 面向超大设备集（>数百设备）
   或附件密文内联进信封（E2EE-061），需要重新评估该阈值；
   目前已做成 `e2ee_envelope_max_bytes` 应用配置，无需改代码即可调整。
