- **Date**: 2026-07-20
- **Repository**: imboy
- **ADR clauses**: ADR 20 §6 S1.3；方向=DID 绑定进 token（用户会话内明确选定）
- **Authorization**: 用户授权作为 P0 漏洞修复；git 身份 leeyi <leeyisoft@qq.com>

## 根因
`token_ds:decrypt_token` 仅返回 uid，token 不含 DID；olm_handler 写端点 `device_id` 取自 body → 同账号任一设备 token 可覆盖别设备密钥。

## 变更（token DID 绑定）
- `src/ds/token_ds.erl`：`encrypt_token/2`、`encrypt_refreshtoken/2`（写 `did` claim）；`decrypt_token` 返回 5 元组含 DID；legacy token 无 claim → `<<>>`。
- `src/ds/auth_ds.erl`：`verify_token` 返回 `{ok, Uid, Did}`；`do_authorization` 注入 `current_did` 进 State；新增 `current_did/1`。
- `src/api/olm_handler.erl`：3 个写端点（report_identity/prekeys/fallback）经 `ensure_device_owner` → 纯谓词 `device_write_decision/2`：body device_id 必须等于 token 绑定 DID，否则 403（device_mismatch）；legacy 空 DID → 403（device_binding_required，fail-closed）。
- `src/logic/passport_logic.erl`：`login_resp/3`、`verify_user/3` 线程登录设备 DID 进 token（密码 + 验证码登录路径）。
- `src/api/passport_handler.erl`：刷新以原 refresh token 的 DID 重签。
- `src/ds/websocket_ds.erl`：decrypt_token 5 元组模式。

## Security negative cases
DT-02（A token 写 B DID → 403）、legacy 无绑定 fail-closed、空 body device_id 拒绝、Unicode 混淆 device_id 拒绝。

## Secrets/log scan
无密钥/明文/PII；token payload 仅加 did claim（设备标识，非秘密）。

## Residual risks / 后续
- **登录路径覆盖**：密码 + 验证码登录已绑 DID；**qr_login_handler、quick_login(jverify) 暂发 legacy token（Did=<<>>）→ 这些路径登录的设备 crypto 写 fail-closed 直到经绑定路径重登**（需后续线程 did header）。
- **兼容影响**：现有已登录用户 token 无 DID → crypto 写 fail-closed 直到重新登录/刷新（refresh 保留 DID，但旧 refresh token 也无 DID）。计划 S1.3 接受。
- **device active 校验**（撤销/禁用设备拒绝上传）属完整可撤销 session = E2EE-030（ADR 16 签字）。
- `websocket_connection_flow_SUITE`（ct，非 eunit）mock auth_ds verify_token 需更新为 3 元组（follow-up）。

## Client Integration & Closed-Loop Verification

1. **Client Device Ownership Guard (E2EE-016 Requirement)**:
   - Verified that `_applyRestoredKeys` in `e2ee_backup_import_page.dart` does not overwrite the physical device DID during key recovery operations. The backup's DID is kept as metadata and displayed in a mask, leaving the native device identity bound and authorized without risk of physical device spoofing.
2. **Device Bound Key Submissions**:
   - Verified that all cryptographic write requests (`E2EEApi().reportDeviceKey`, `OlmApi().reportIdentity`, `OlmApi().reportPrekeys`, and `OlmApi().reportFallbackKey`) transmit the device ID alongside HTTP auth tokens. Since the backend binds the authentication token's `did` claim during the login phase, all keys are safely associated with authenticated device ownership.
3. **Robust Backend Verification**:
   - Verified that the backend tests (`token_ds_tests`, `auth_ds_tests`, and `olm_handler_tests`) compile and execute with 100% success on the Erlang node. These tests robustly confirm that trying to overwrite keys using a token belonging to another device correctly results in a `403 device_mismatch` fail-closed error.
