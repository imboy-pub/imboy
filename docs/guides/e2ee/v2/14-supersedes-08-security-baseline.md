# ADR 14 — 行业顶级 E2EE 安全基线与发布治理

> **状态**：**Accepted**（2026-08-02 leeyi solo 一人决策全签，单人开发一人兼五方；此前为范围收敛豁免 2026-07-20，豁免限制解除，全文生效。ADR 19 MLS 除外——维持 Proposed，见 ADR 31）
> **拟替代**：ADR 08 的威胁边界、可追溯矩阵与发布判定；补充 ADR 00/01 的治理闸门
> **关联提案**：ADR 15–19；实施与验收见 `20-implementation-and-acceptance-plan.md`
> **触发原因**：2026-07-20 实现复核表明，当前系统仍有未认证的 legacy fallback、设备身份未绑定登录会话、恢复材料不完整、合规路径 fail-open、群聊缺少可证明 PCS 等差距，不能宣称达到行业顶级产品水平。

---

## 1. 决策摘要

IMBoy 的 E2EE 不再以“存在加密算法”作为完成标准，而以端到端可验证的安全属性作为发布标准：

1. **Strict C2C**：每个接收设备独立使用 Olm/Double Ratchet；新消息不得使用 RSA 或 Megolm；无安全共同套件时拒发。
2. **Strict Group**：以 RFC 9420 MLS 1.0 为最终目标；MLS 达标前，Megolm 仅可标记为 `Strong Preview`，不得标记为“行业顶级群聊 E2EE”。
3. **认证信封**：所有影响消息语义与路由的字段必须被密码学绑定；服务端可丢弃、延迟或重排消息，但不能无痕篡改其语义。
4. **设备身份**：所有密钥上传、领取、撤销和信任事件都绑定 `(uid, device_id, session_id)`，并由设备密钥签名。
5. **可验证信任**：引入账号级 cross-signing 与 key transparency，降低被攻陷服务端静默替换设备密钥的能力。
6. **恢复不克隆活跃身份**：新设备必须生成新 `device_id` 和活跃 ratchet；只恢复账号信任根与只读历史解密材料。
7. **模式分域**：Strict 与 Compliance 是两个不同的信任模型和产品承诺；两者都 fail-closed，但 Compliance 必须明确展示审计接收方。
8. **事务化 CryptoStore**：消息提交、ratchet/epoch 状态更新和去重记录必须原子持久化，崩溃不能导致密钥重用或状态倒退。

本提案通过人工签字后，ADR 08 中与上述决策冲突的“部分防御/显式接受”不再作为 GA 依据；历史兼容仍按 ADR 15 的 decrypt-only 规则保留。

## 2. 声明范围

本路线覆盖：C2C/群消息正文、E2EE 控制消息、附件内容与附件密钥、设备身份、历史密钥恢复和 Compliance 审计接收方。

以下能力未在本路线验收前，不能包含在“行业顶级 E2EE”的声明中：音视频通话、推送通知正文、端侧搜索索引、导出后的文件、截图/录屏、流量元数据隐藏。若产品界面把这些能力统一称为“聊天 E2EE”，必须分别补充威胁模型和验收，不得用消息协议的验收结果外推。

## 3. 产品安全等级

| 等级 | 可对外表述 | 必须满足 | 禁止表述 |
|---|---|---|---|
| `Experimental` | 实验性加密 | 单元测试可运行 | 安全、生产可用 |
| `Preview` | E2EE 预览 | 密文传输、基础篡改检测、已知风险公开 | 顶级、Signal 级、MLS 级 |
| `Strong Preview` | 强 E2EE 预览 | ADR 15–18 的 P0/P1 门禁通过，遗留群聊限制公开 | 行业顶级群聊 E2EE |
| `GA-C2C` | 生产级单聊 E2EE | C2C Olm per-device、认证信封、设备绑定、cross-signing、透明度、恢复与外审门禁通过 | 群聊 MLS 已完成（若未完成） |
| `GA-Top-Tier` | 行业顶级 E2EE | `GA-C2C` + MLS 群聊 + 独立互操作 + 外部审计 + 运行门禁全部通过 | 无条件“绝对安全” |

任何营销、README、应用内文案和管理后台不得高于当前通过的等级。等级由发布证据决定，不由功能开关或版本号决定。

## 4. 受保护资产与安全不变量

### 4.1 受保护资产

| 资产 | 目标 | 允许获知者 |
|---|---|---|
| 消息正文与附件密钥 | 机密性、完整性、发送设备真实性 | 目标会话中被授权且未撤销的设备；Compliance 模式另含明确审计设备 |
| 设备身份私钥、cross-signing 私钥 | 永不出现在服务端、日志、崩溃报告和明文备份 | 本设备安全存储；加密恢复包按 ADR 17 |
| Olm/MLS 活跃 ratchet 状态 | FS/PCS、单调演进、不可克隆 | 活跃设备本地 CryptoStore |
| 历史解密材料 | 最小权限、只读、可撤销 | 经授权恢复的设备 |
| 设备列表、密钥版本、透明度头 | 完整性、一致性、可审计 | 客户端与透明度服务；内容可公开但不可伪造 |
| 模式与合规密钥清单 | 防降级、防替换、可见 | 客户端、组织策略管理者 |

### 4.2 必须长期成立的不变量

1. 服务端、DBA、对象存储管理员和反向代理只持有密文与必要元数据，不能解密 Strict 内容。
2. 恶意服务端不能通过替换 `from/to/gid/msg_type/device_id/session_id/epoch` 使客户端接受另一种语义。
3. Strict 模式任何缺钥、验签失败、身份回滚、策略未初始化、透明度不一致都必须拒发或拒收，不得静默走 RSA、明文或陈旧合规键。
4. 被撤销设备不能获得撤销后的新会话秘密；新加入群的设备不能解密加入前内容；被移除设备不能解密移除后的内容。
5. 设备攻陷后的安全恢复需要新的 Olm DH ratchet 或 MLS Commit；仅重新启动、重新登录或换 token 不算 PCS。
6. 同一活跃发送 ratchet/MLS leaf 不得在两台物理设备上并行使用。
7. 所有密码学状态更新要么与消息状态同时提交，要么全部回滚；不得出现“密文已发送但 ratchet 状态未推进”的可重复密钥状态。
8. 所有输入在分配大内存、执行 KDF 或进入密码学库前完成长度、枚举、版本和资源上限校验。

## 5. 威胁模型

### 5.1 必须防御

| ID | 攻击者能力 | 必须提供的防御 |
|---|---|---|
| T1 | 服务运营者读取 DB、日志、对象存储 | E2EE、日志脱敏、服务端零私钥 |
| T2 | 服务端被完全攻陷，可替换 API/WS 响应 | 签名设备清单、cross-signing、透明度一致性、认证信封、防降级 |
| T3 | 网络攻击者读取、篡改、重放流量 | TLS + E2EE 完整性 + replay window/idempotency |
| T4 | 恶意已登录设备冒充同账号另一设备 | device-bound session、设备签名、目标设备授权 |
| T5 | 单设备短期攻陷并随后恢复控制 | Double Ratchet/MLS PCS、撤销、密钥更新、最小备份 |
| T6 | 加密备份被盗并离线暴力破解 | Argon2id、有界参数、随机恢复密钥、格式认证 |
| T7 | 恶意客户端构造畸形/超大/回滚输入 | 严格解析、单调版本、配额、原子 claim、模糊测试 |
| T8 | 服务端对不同用户展示不一致设备历史 | append-only transparency、inclusion/consistency proof、gossip |
| T9 | 崩溃、断电、并发收发造成状态分叉 | 事务化 CryptoStore、WAL、幂等操作、恢复测试 |
| T10 | 供应链依赖或 FFI 边界缺陷 | 锁定版本、SBOM、签名构建、独立互操作、外审和 fuzz |

### 5.2 明确不防御

- 已完全控制且持续控制合法端点的攻击者可以读取该端点当时可见的消息。
- 服务端可以拒绝服务、延迟、丢弃或选择性转发；客户端负责可见告警，E2EE 本身不能保证可用性。
- 流量模式、IP、发送时间、目标账号/群、粗略消息长度等传输元数据仍可能可见；“密封发送者”和流量填充不在本轮范围。
- 用户主动扫描并确认攻击者控制的设备，或在系统明确告警后强制降级，无法由密码学完全阻止；Strict 模式不提供“仍然发送”旁路。
- 操作系统内核、键盘、无障碍服务或屏幕录制被控制时，应用层 E2EE 无法保护输入输出明文。

以上边界必须进入产品安全说明，不能用“端到端加密”四个字掩盖。

## 6. 非功能目标与预算

以下是 GA 候选版在**最低受支持真机**上的发布预算，不以模拟器结果替代：

| 维度 | 预算/要求 | 证据 |
|---|---|---|
| C2C 加/解密开销 | 单条 4 KiB 文本 p95 ≤ 100 ms，p99 ≤ 200 ms | Android/iOS 真机基准，冷热启动分开 |
| MLS 应用消息 | 4 KiB p95 ≤ 50 ms；1000 设备 Commit p95 ≤ 2 s | 两平台真机 + 内存峰值报告 |
| 内存安全 | 10 MiB 上限输入不得导致 OOM；备份解析峰值 ≤ 输入大小 3 倍且 ≤ 64 MiB | fuzz/resource tests |
| 可靠性 | 10,000 次 kill/restart 注入中，密钥重用、state rollback、已确认消息永久不可解均为 0 | crash consistency harness |
| 互操作 | 规范向量 100% 通过；Flutter 与独立实现双向向量 100% 通过 | CI artifact |
| 安全回归 | Critical/High 测试 0 skip；外部审计 Critical/High 未修复项为 0 | CI + 审计报告 |
| 秘密清理 | logout/account switch 后，安全存储、数据库密钥、活跃会话状态读取均为空；旧 DB 无旧密钥不能打开 | 自动化 + 真机取证 |

若最低设备无法达到预算，必须在 ADR 中修改支持范围或优化实现；不得跳过性能/可靠性门禁。

## 7. 发布与运行治理

### 7.1 三道独立门禁

1. **设计门**：ADR 14–19 由产品负责人、客户端负责人、后端负责人、安全 reviewer 签字。
2. **实现门**：ADR 20 对应自动化、真机、互操作、迁移和回滚证据全部归档。
3. **安全门**：独立密码学审计完成，Critical/High 清零；修复项回归由审计方或独立 reviewer 复核。

任一门未通过，最多发布到上一安全等级。

### 7.2 灰度规则

- 以 capability + server feature flag 控制新写入；客户端始终保留 legacy decrypt-only。
- 灰度指标仅收集协议版本、成功/失败类别、耗时和状态机事件，不收集消息明文、密钥、密文全文或 Safety Number。
- 发现身份错绑、认证信封接受篡改、密钥重用、跨 epoch 解密等事件时立即停止新写入灰度。
- 回滚只能停止新协议写入或回到先前安全写入路径；**不得重新开启 Strict 的 RSA/明文/未认证 room-key fallback**。

## 8. 失败模式与响应

| 失败 | 用户行为 | 系统行为 | 运维行为 |
|---|---|---|---|
| 签名/透明度验证失败 | 显示安全阻断，不提供静默继续 | 隔离设备清单，不建立新会话 | 告警并比对 signed tree head |
| OTK/KeyPackage 耗尽 | 显示暂时无法安全发送 | 有界重试；不降级 | 按目标设备限流告警 |
| CryptoStore 提交失败 | 消息保留“未发送” | 回滚密文与 ratchet 事务 | 采集无秘密错误码 |
| 收到未知/超前版本 | 显示无法解密或等待升级 | 严格拒绝，不猜测 fallback | 统计兼容性指标 |
| Compliance 清单缺失/过期 | 显示组织策略不可用 | 拒发 | 通知组织管理员轮换 |
| MLS fork/epoch gap 超限 | 显示群安全状态异常 | 停止应用消息，执行受认证 resync | 告警并保全无秘密证据 |

## 9. 被否决替代方案

| 方案 | 否决原因 |
|---|---|
| 在现有路径继续打补丁并宣称顶级 | 不能解决信任、恢复、群 PCS 和状态原子性四个系统性问题 |
| 自研 Signal/MLS 密码学原语 | 审计面和实现风险不可接受；应使用维护中的成熟实现并做互操作 |
| Strict 允许 RSA/Megolm 自动 fallback | 恶意服务端可利用能力/字段替换制造降级，安全承诺不可验证 |
| 恢复完整克隆旧设备 | 克隆活跃 ratchet 和 DID，造成 nonce/key reuse、身份并发和撤销歧义 |
| 把合规私钥交给服务端 | 直接破坏服务端零知识边界，Strict 与 Compliance 都失去可信解释 |

## 10. 接受与生效

提案只有在以下人员签字后才生效：

- [ ] 产品/安全承诺负责人：确认等级命名和不防御边界
- [ ] Flutter/移动端负责人：确认 CryptoStore、FFI、真机门禁可执行
- [ ] Erlang/后端负责人：确认 device-bound auth、透明度和限流可运维
- [ ] 独立安全 reviewer：确认协议组合和验收用例足以证伪关键声明
- [ ] 发布负责人：确认灰度、观测、回滚不引入不安全 fallback

签字后执行两个治理动作：

1. 在 ADR 08 顶部增加 `Superseded in part by ADR 14`，明确仍保留的历史说明；
2. 把 ADR 14–19 加入 00 Freeze Gate 和 10 依赖图。

未签字前，不修改 00–13，且当前产品等级保持 `Preview`。
