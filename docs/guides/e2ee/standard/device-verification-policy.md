# 设备验证策略（Device Verification Policy）

> 对应 **TT-B5**（SHOULD）：「未验证设备的能力边界是**显式策略**，非实现缺陷」。
> 最后核对：2026-08-02 ｜ **策略选型 🔒 待拍板，见 §4**

## 1. 今天的事实状态（先说清楚，再谈策略）

### 1.1 **不存在「已验证设备」这个层级**

`safety_number.dart` 生产零调用（IMB-2026-006），`identity_verifier` 只被
`olm_session_service` 引用。**用户没有任何途径把一台设备标记为"已验证"。**

所以 TT-B5 问的「未验证设备能做什么」，今天的答案是：
**所有设备都是未验证设备，能做全部事情。** 这不是一条策略，是策略缺位。

### 1.2 唯一实际生效的门：TOFU

`olm_session_service.dart` `_enforceTofu`：

| 情形 | 行为 |
|---|---|
| 首次见到某对端设备 | **固定** 其 identity fingerprint（Trust On First Use） |
| fingerprint 与已固定值不符 | **fail-closed** —— 抛 `IdentityChangedException`，不解密 |
| `CryptoStore` 不可用 | ⚠️ **降级为无 TOFU，不阻塞通信** |

### 1.3 一条此前无文档记载的降级

上表最后一行是**实质性的策略决定**，但此前只以一行代码注释存在：

```dart
if (store == null) return; // 降级：无持久化则跳过 TOFU
```

**含义**：本地存储出问题时，identity 变化检测**整体失效**，通信照常进行。
这是 fail-open。它的合理性与 `is_active` 的 fail-open（IMB-2026-014）同源——
fail-closed 会让存储故障直接切断所有通信——但**上限不同**：
`is_active` 有 60s 缓存 TTL 封顶，本条**没有任何时间或次数上限**，
故障持续多久就裸奔多久，且用户无感。

> **在选定 §4 策略之前，这就是当前的实际策略。**

---

## 2. TT-B5 要求什么

不要求"必须强制验证"，要求**能力边界是显式的**：
未验证设备可否收发 E2EE 消息、可否加入群、可否读历史，必须有明文规定，
而不是"代码碰巧这么写"。

参照先例：Element 于 2026-10 生效的强制验证公告。

---

## 3. 前置：无论选哪个策略都必须先做的事

**Safety Number 接线（P3-4 / P3-5）是所有选项的共同前提。**
没有它，用户无法完成验证动作，任何"区别对待未验证设备"的策略都只会变成
"惩罚全部用户"。

因此 §4 的选项**在 IMB-2026-006 关闭前均不可实施**。本文档先把决策空间定下来，
是为了让 P3-4/P3-5 的实现有明确目标，而不是实现完再回头想要什么。

## 4. 选项空间 🔒 待拍板

| 选项 | 未验证设备能力边界 | 代价 |
|---|---|---|
| **A. 维持现状** | 无差别，全部允许 | TT-B5 永远不达标；T2/T8 无缓解手段 |
| **B. 软提示**（推荐起点） | 全部允许，但会话内显示未验证徽标 + 首次会话一次性提示 | 实现成本最低；对用户零阻断；但依赖用户主动性，实际验证率通常很低 |
| **C. 高风险操作前强制** | 日常收发允许；**转账 / 改密 / 导出备份 / 加入敏感群**前要求验证 | 需定义"高风险操作"清单；阻断点少而准 |
| **D. 全面强制**（Element 路线） | 未验证设备**不可收发 E2EE 消息** | 最强；但换机、重装、多设备场景下极易把用户锁在门外，客服成本高 |

### 我的推荐

**B 作为第一步，C 作为目标态，暂不做 D。**

理由：
- D 的失败模式是**用户被自己的加密锁在外面**。对一个还没有成熟客服体系的产品，
  这个代价高于它挡住的威胁。Element 敢做，是因为其生态已有成熟的多设备恢复路径。
- B→C 是渐进的：先让"未验证"这个状态在 UI 里可见（B），积累出真实验证率数据，
  再决定 C 的阻断清单该有多长。
- 无论 B 还是 C，都比今天的"策略缺位"强，且都不会把用户锁死。

**这是建议不是决定。** 选型涉及产品体验与客服成本，需你拍板。

### 同时需要决定的第二件事

§1.3 那条 **`CryptoStore` 不可用时跳过 TOFU** 的 fail-open，是否要加上限？

① 维持无上限（现状） ② 加时间/次数上限，超限后 fail-closed
③ 降级期间禁止**新建**会话，只允许已有会话继续

推荐 ③：新建会话是 MITM 最有价值的注入点，而已有会话有历史 fingerprint 保护。
