## 第一章 可用性目标

### 1.1 服务可用性定义

**可用性**（Availability）= （月度总分钟数 - 停机分钟数）/ 月度总分钟数 × 100%

以下情况**不计入停机时间**：

- 提前 48 小时通知的计划维护窗口（每月不超过 4 小时）
- 由甲方网络、设备或第三方服务（支付网关、推送服务）引起的不可用
- 不可抗力（自然灾害、政府管制、运营商大规模故障）

### 1.2 可用性级别与目标

| 服务级别 | 月度可用性 | 月停机上限 | 年停机上限 | 适用版本 |
|---------|-----------|-----------|-----------|---------|
| 标准版 | 99.5% | 约 216 分钟 | 约 43.8 小时 | 基础私有化部署 |
| 专业版 | **99.9%** | **约 43 分钟** | **约 8.7 小时** | 含 HA 部署的专业版 |
| 旗舰版 | 99.95% | 约 21 分钟 | 约 4.4 小时 | 多地域主动-主动 |

> 本协议默认适用 **99.9%（专业版）** 目标。如需其他级别，在签约时于此处注明。

### 1.3 补偿标准

当月可用性不达标时，乙方提供服务费抵扣（不退款）：

| 实际可用性 | 补偿额度（当月服务费比例）|
|-----------|----------------------|
| 99.0% ~ 99.9% | 10% |
| 95.0% ~ 99.0% | 25% |
| < 95.0% | 50% |

**补偿申请**：甲方须在停机结束后 **30 个自然日**内提交申请，逾期不予受理。每月补偿上限为当月合同服务费的 50%。

## 第二章 性能目标

### 2.1 API 响应时间

测量方式：Prometheus `http_request_duration_seconds` 指标，99 分位（P99），工作日业务高峰期（09:00–22:00）。

| 接口类型 | P95 目标 | P99 目标 | 说明 |
|---------|---------|---------|------|
| 登录认证 (`/api/v1/passport/*`) | < 200ms | < 500ms | 含 RSA 解密 |
| 消息发送 (`/api/v1/msg/*`) | < 100ms | < 300ms | 不含消息推送延迟 |
| 用户信息读取 | < 50ms | < 150ms | depcache 命中 |
| 文件 presign URL 获取 | < 150ms | < 400ms | 含 Garage 签名 |
| 群组管理操作 | < 200ms | < 500ms | 成员数 < 500 |
| 管理后台查询 | < 500ms | < 2s | 含分页聚合 |

### 2.2 WebSocket 连接性能

| 指标 | 目标 | 测量方式 |
|------|------|---------|
| WS 握手建立时间 | < 1 秒（P95） | 客户端侧计时 |
| 消息端到端延迟（在线用户） | < 500ms（P95） | 发送 → 接收方 ACK 时间差 |
| 消息离线补投延迟 | < 5 秒 | 接收方重新上线后首次拉取 |
| 单节点最大 WS 在线数 | 50,000 | Prometheus `ws_connections_current` |

### 2.3 吞吐量基准

以下为单节点（8 核 16GB）基准测试数据，实际环境可能因业务模型不同而有差异：

| 场景 | 吞吐量 |
|------|--------|
| HTTP API 峰值 QPS | 3,000 |
| WebSocket 消息峰值 | 10,000 条/秒 |
| 并发 WS 连接 | 50,000 |
| 数据库连接池容量 | 80 连接（`IMBOY_PG_MAX_COUNT`）|

## 第三章 故障响应标准

### 3.1 故障级别定义

| 级别 | 名称 | 定义 | 示例 |
|------|------|------|------|
| P0 | 全站严重故障 | 核心服务完全不可用，影响 > 50% 用户 | 所有用户无法登录、数据库宕机、消息无法收发 |
| P1 | 重大功能故障 | 核心功能降级，影响 10%~50% 用户 | WebSocket 频繁断开、部分消息延迟 > 30 秒、文件上传失败 |
| P2 | 局部功能故障 | 非核心功能异常，影响 < 10% 用户 | 消息搜索不可用、特定群组异常、管理后台部分页面错误 |
| P3 | 轻微问题 | 性能轻微下降、告警但无实际影响 | 响应时间略超基准、日志警告、边缘场景 bug |

### 3.2 响应与恢复时间目标

| 级别 | 首响时间（自告警触发起）| 临时恢复目标（RTO 参考）| 根因报告时限 |
|------|----------------------|----------------------|------------|
| P0 | **15 分钟** | **2 小时** | 24 小时内 |
| P1 | **30 分钟** | **4 小时** | 48 小时内 |
| P2 | **2 小时** | **8 小时（下一工作日）** | 1 周内 |
| P3 | **1 个工作日** | **下次迭代** | 下次迭代 |

> 首响时间：乙方技术人员确认告警并开始处置。响应不等于解决。

### 3.3 故障通报渠道

| 场景 | 通报方式 |
|------|---------|
| P0/P1 发生时（自动）| 乙方监控系统 PagerDuty / 企业微信机器人推送 |
| P0/P1 发生时（人工补充）| 电话通知甲方技术联系人（15 分钟内）|
| P2/P3 | 工单系统（`[工单地址]`）|
| 月度服务报告 | 每月 5 日前发送至甲方邮件 |

## 第四章 备份与恢复目标

### 4.1 备份策略

| 数据类型 | 备份频率 | 备份方式 | 保留周期 |
|---------|---------|---------|---------|
| PostgreSQL 全量 | 每日 02:00 | `pg_dump` 压缩 + Garage S3 offsite | 30 天 |
| PostgreSQL 增量（WAL） | 实时 | pg_basebackup / WAL-G | 7 天 |
| Garage S3 附件 | 每日 03:00 | `rclone sync` 至异地存储 | 90 天 |
| imboy 应用配置 | 每次发布前 | Git tag + `/etc/imboy/` 归档 | 永久 |
| 日志（Loki） | 实时写入 | 本地磁盘 + 压缩轮转 | 180 天 |

备份脚本：`imboy/scripts/backup_pg.sh`、`imboy/scripts/backup_garage.sh`

### 4.2 RPO / RTO 目标

| 指标 | 定义 | 目标 |
|------|------|------|
| RPO（恢复点目标）| 可接受的最大数据丢失量 | **< 4 小时**（含 WAL 实时备份时降至 < 15 分钟）|
| RTO（恢复时间目标）| 从故障到恢复服务的时间 | **< 2 小时**（数据库 + 应用全量恢复）|

### 4.3 恢复演练

乙方承诺每季度执行一次恢复演练：

- 在非生产环境完整恢复最近备份
- 验证数据完整性（行数比对、关键 API 冒烟测试）
- 记录实际 RTO，与目标比对
- 演练记录格式参照 `docs/guides/operations/deployment/RESTORE-DRILL-2026-06.md`

甲方可申请参与观摩演练，须提前 5 个工作日告知。

## 第五章 维护窗口

### 5.1 计划维护规定

| 规定项 | 内容 |
|--------|------|
| 通知时限 | 常规维护提前 **48 小时**通知甲方；紧急安全补丁提前 **4 小时**通知 |
| 维护窗口 | 每周三 **02:00–06:00**（UTC+8）为低峰窗口；如甲方业务特殊，可协商调整 |
| 月度上限 | 每月计划维护不超过 **4 小时**（不计入 SLA 停机时间）|
| 维护内容 | 提前通知内容须说明：维护目的、预计时长、影响范围、回滚计划 |

### 5.2 发布流程

| 类型 | 频率 | 流程 |
|------|------|------|
| 功能版本（Minor）| 每 4~8 周 | 测试环境验收 → 灰度 5%→50%→100% → 监控 24h |
| 补丁版本（Patch）| 按需 | 修复验证 → 直接发布 → 监控 4h |
| 安全热补丁 | 紧急 | 同步通知 → 立即发布 → 回滚预案就位 |

## 第六章 支持与升级路径

### 6.1 支持层级

| 层级 | 内容 | 响应渠道 | 服务时间 |
|------|------|---------|---------|
| L1 基础支持 | 常见问题解答、文档指引 | 工单系统 | 工作日 09:00–18:00 |
| L2 技术支持 | 配置问题、功能咨询、故障排查 | 工单 + 远程会议 | 工作日 09:00–18:00 |
| L3 专家支持 | 深度故障分析、性能调优、架构咨询 | 专线联系（仅旗舰版）| 7×24（P0/P1 专属）|

### 6.2 版本支持周期

| 版本类型 | 主要功能支持 | 安全补丁支持 | 服务终止（EOL）|
|---------|-----------|------------|--------------|
| 当前主版本（v2.x）| 是 | 是 | 待定（发布 v3.0 后 18 个月）|
| 上一主版本（v1.x）| 否 | 是（至 2027-06-30）| 2027-06-30 |
| 更早版本 | 否 | 否 | 已终止 |

> 建议甲方在新版本发布后 **6 个月内**完成升级。乙方提供升级支持服务。

### 6.3 升级支持内容

标准升级支持（含于服务合同内）：

- 升级前：环境评估、兼容性检查、迁移数据库变更（erlang_migrate 工具）
- 升级中：远程协同执行、回滚预案待命
- 升级后：24 小时紧密监控、日志审查

## 第八章 协议条款

### 8.1 生效与终止

- 本 SLA 随服务合同签署生效，合同终止时同步终止。
- 甲方可每 12 个月提出一次 SLA 条款复审，乙方 30 日内书面回复。

### 8.2 例外与免责

以下情况乙方不承担 SLA 补偿责任：

- 甲方或甲方用户行为导致的故障（超量请求、错误配置、恶意操作）
- 甲方未按乙方建议完成安全加固导致的安全事件
- 第三方基础设施故障（云服务商、CDN、支付网关）
- 不可抗力（法律定义范围内）
- 甲方拒绝执行建议的升级或补丁导致的故障

### 8.3 责任上限

乙方因 SLA 不达标所承担的最高赔偿累计不超过甲方最近 3 个月实付服务费总额。

### 8.4 争议解决

双方因本 SLA 产生争议，优先协商解决；协商不成，提交 `[约定仲裁机构/管辖法院]` 解决。
