# E2EE 后端只读审计盘点

> 审查日期：2026-07-02 ｜ 方式：只读盘点，未修改任何代码 ｜ 仓库：`imboy`（Erlang/OTP，Handler→Logic→DS→Repo）
> 审查目标：核对「服务端全程不接触明文私钥」在所有路径成立，聚焦密钥轮换、换设备恢复、分片传输、清理边界四个历史审计可能未覆盖面。

## 总结论

**「服务端全程不接触明文私钥」在所有生产可达的 HTTP 路径上成立**：transfer / social / recovery / backup / cleanup 五条路径均只做密文路由与存储，业务层零处调用解密原语，日志无密钥材料泄漏，密码学参数全部正确。

**但零信任架构的三大配套支柱各有一根是断的**：审计日志从未成功写入过一条正确记录（模块名冲突）、社交恢复分片永不失效可无限重放、账号注销不清理任何 E2EE 表。另有两条恢复路径是功能孤岛（同账号设备传输被 handler 拒绝、本地备份 create 端点不存在）。

## 按维度核对结果

### 1. 零接触核对 ✅ 成立（生产路径）

- **transfer**：`src/api/e2ee_transfer_handler.erl:95-96` 起全链路只透传 `encrypted_key_bundle`，全库无对它的解密调用。
- **social**：`src/logic/e2ee_social_logic.erl:35-38`（"C1 FIX：客户端已完成 Shamir 分割和代理公钥加密，服务端只存储"）；`recover_key` 走 `validate_shards/2`（:168-177）只做数量门禁不重组；`decrypt_shard`（`src/api/e2ee_social_handler.erl:246-258`）只返回加密分片。
- **backup**：`src/repo/e2ee_local_backup_repo.erl:11-14` 表只有元数据列（checksum/device_id/version），无 blob 列，设计上就不存备份内容。
- **解密原语范围**：grep 全部 e2ee 模块，`crypto:`/`public_key:` 零调用；`elib_cipher:decrypt_rsa_oaep/decrypt_private_key` 在 E2EE 业务域无生产调用方（服务端唯一用私钥解密的场景是登录口令 RSA，属鉴权域）。
- **二元组陷阱**：`(BackupId, Uid)`、`(Uid, DeviceId)`、`group_ds:is_member(Uid, Gid)`、`get_proxy_shard(ShardId, ProxyUid)` 全链路定义与调用点顺序逐一比对，**未发现错位**。
- **日志泄漏**：全部 `?ERROR_LOG/?INFO_LOG` 逐条核对，只记 uid/device_id/错误原因等元数据，无密文/密钥字段入日志。

**唯一污点（死代码）**：`e2ee_social_ds:create_key_shares/5`（`src/ds/e2ee_social_ds.erl:113-178`）仍接收明文 `PrivateKeyPem` 形参做服务端 Shamir 分割，唯一调用方是自身单测——与「ad60fde2 那轮之后含死代码全清」的旧结论矛盾，07-02 grep 复核确证漏删。

### 2. 密钥分发 ✅ 鉴权闭环

- `/v1/e2ee/user_keys`：JWT 鉴权 + `ensure_e2ee_enabled` 闸门；任意登录用户可查任意 uid 公钥属设计如此（`src/logic/e2ee_logic.erl:18-21`），返回列仅 `device_id/device_type/public_key/key_id/last_active_at`（`src/repo/user_device_repo.erl:52,88`），**无私钥字段混入**（表本身无 private_key 列）。
- `/v1/e2ee/group_member_keys`（注意：实际是 /v1，不存在独立 /v2）：`group_ds:is_member(CurrentUid, Gid)` 前置校验（`src/logic/e2ee_logic.erl:25`），非成员 403，无法枚举群成员公钥。
- 全部 e2ee/user_device 端点均不在 `imboy_router:open/0` 白名单（`src/imboy_router.erl:900-953`），无绕过鉴权的端点。

### 3. 密钥轮换 ⚠️ 服务端无版本历史

- **现象**：轮换是纯 UPDATE 原地覆盖（`src/ds/user_device_ds.erl:150-157`），表唯一约束是 `(user_id, device_id)`（迁移 `priv/migrations/00000001_foundation.up.sql:2743-2744`），无 kid 历史表。客户端消息里的 `kid` 服务端不感知、不路由——「旧密文路由到旧 key」在服务端层面完全不存在。
- **并存窗口**：轮换后异步通知好友清缓存（`src/logic/e2ee_logic.erl:100-126`），但公钥缓存 TTL 30 分钟，窗口内旧公钥密文仍会产生。
- **定性**：两条均已在 `docs/standards/e2ee-key-rotation-policy.md`（3.2/6.4 节）书面承认为设计权衡（"轮换=历史消息不可解密，需提前本地备份"），是已知取舍而非隐藏 bug → 列 P1 而非 P0。

### 4. 换设备恢复 🔴 三条路径两条断、一条可重放

- **设备间传输（优先级1）功能性断裂**：`src/api/e2ee_transfer_handler.erl:104-105` 显式拒绝 `ToUid =:= CurrentUid`，但本系统同账号换新机恰恰是 FromUid==ToUid——最常见的换机场景走不通这条「最快最安全」的路径。
- **本地备份（优先级3）是孤岛**：路由只注册了 `backup/list` 和 `backup/delete`（`src/imboy_router.erl:265-266`），create 端点不存在，`e2ee_local_backup_repo:create/1` 全库无调用方，Flutter 客户端也只实现了 list/delete → 表恒空，`check_local_backup_available/1` 恒 false。
- **社交恢复（优先级2）可无限重放**：`decrypt_shard` 只读不消费，全库无任何路径把分片 status 置 `'used'`，`delete_restored_shards/2` 唯一调用方是单测 → 任意 2 个（threshold 判 2）代理可在任意时间点合谋重建用户私钥，用户无感知。且**撤销可信联系人不级联撤分片**（`remove_trusted_contact` 只删联系人表，`get_proxy_shard` 鉴权不 JOIN 回信任表）。
- **鉴权强度**：全部仅 JWT + 设备归属校验，无恢复码/PIN 派生因子。被盗 JWT 无法直接窃私钥（服务端本就没有），但可诱导账号间私钥转移语义（依赖上面 ToUid≠CurrentUid 的语义澄清）。
- **新设备解不开旧密文的兜底**：服务端无旧私钥迁移/重加密路径，与既有评估文档结论一致——【跨端议题，列出不计分】。

### 5. 分片传输 🔴 审计链失效 + WS 归属校验缺口

- **稳健面**：`shard_index/total_shards` 由服务端 `lists:seq` 生成，客户端不可控，无乱序/越界注入；REST 端 `is_trusted_contact` + `get_shard_by_id/get_proxy_shard` 归属校验闭环；transmission_log 设计上不含密文。
- **审计日志全灭**（根因见维度7）：4 个调用点传参按 lib stub 签名，实际路由到 logic 实现，参数位置错位 → uid 列被填原子、shard_id 被填 map，INSERT 必败且 `{error,_}` 被吞（`src/logic/e2ee_shard_validator.erl:64-72`）→ **零信任赖以自证的分片审计与异常检测从未有过一条正确数据**。测试用按 stub 签名写的 meck 把 bug 挡在门外，且 `test/logic/e2ee_social_logic_tests.erl` 还在调已不存在的 `create_shards/6`，测试网本身破洞。
- **WS relay 归属校验缺口**：`store_shard/shard_stored/decrypt_shard`（`src/logic/msg_s2c_logic.erl:141-211`、`src/logic/msg_c2s_logic.erl:304-346`）的 shard_id/to 全部取自客户端 Payload，不查库核实归属即转发——任何登录用户可向任意人发伪造分片状态消息（骚扰/状态混淆，非密文泄漏）。
- **重放**：REST create_shards 无幂等键，客户端重试产生语义重复分片；transmission_log 表无任何清理机制。

### 6. 清理边界 ⚠️ 一处误伤、一处漏清

- **触发**：`src/imboy_sup.erl:95-103` 常驻 worker，默认启用、5 分钟一轮（配置项存在但 config/ 从未显式设置）。
- **误伤活跃会话**：清理条件 `status IN ('pending','accepted')` 且 `expires_at` 从创建起硬编码 300 秒、**accept 后不延长** → 用户 accept 后犹豫超时，confirm 必失败。（`src/logic/e2ee_transfer_logic.erl:51`、`src/repo/e2ee_transfer_repo.erl:127-141`）
- **无 TOCTOU 竞态**（稳健）：业务读写与 cleanup 用同一数据库时钟谓词 `expires_at > NOW()`，行未删也已视为 not_found；`update_status_and_device` 有 CAS。
- **漏清**：cleanup 只管 `e2ee_transfer_sessions`；`e2ee_social_shards`（真正的分片表）无任何清理；**账号注销 `user_ds:delete_all_related_data`（:225-266）清 12 张表无一张 e2ee_*** → 已注销用户的加密私钥分片永久滞留，叠加「分片可无限重放」，历史代理合谋可重建已注销用户的私钥——安全 + 被遗忘权双重缺口。
- 清理失败仅记日志无告警；单次失败不停摆 worker（稳健）。

### 7. 重复模块判定 🔴 不是简单死代码，是同名冲突

`src/lib/e2ee_shard_validator.erl`（stub，`(atom, term, map) -> ok` 空实现）与 `src/logic/e2ee_shard_validator.erl`（真实现，`(int, int, binary)` 落库）**声明同一个 `-module(e2ee_shard_validator)`**。erlang.mk 把两份都编进 `ebin/`，后编译覆盖先编译——`beam_lib` 实证当前生效的是 **logic 版**；但全部 4 个调用方（`src/logic/e2ee_social_logic.erl:120`、`src/logic/msg_c2s_logic.erl:321`、`src/logic/msg_s2c_logic.erl:161,196`）按 **lib 版签名**传参。结论：**两份都不是调用方期望的契约**，lib 版是被覆盖的僵尸，logic 版是签名对不上的活代码。

## 已核实稳健（带证据，无需补强）

1. 五条路径服务端零接触明文私钥（生产可达面），业务层零解密原语调用。
2. 密码学（`src/lib/elib_cipher.erl`）：AAD=Salt 加解密两端一致、Tag 固定 16 字节、IV 每次 `strong_rand_bytes(12)` 不重用、OTP `crypto_one_time_aead` InText 在 AAD 前（未踩 OTP28 坑）、RSA-OAEP-SHA256 两端参数一致。
3. user_keys / group_member_keys / decrypt_shard / create_shards / transfer/accept 鉴权全部闭环；跨用户设备操作在 SQL 层被 `user_id=$1` 硬性阻断。
4. transfer 会话并发防护：唯一约束捕 23505 + CAS `WHERE status='pending'` + TTL 谓词一致无 TOCTOU。
5. 二元组参数顺序全链路核对无错位；日志无密钥材料泄漏。

## 改动建议（本轮未动任何代码，供后续立项）

1. **合并 shard_validator**：删 `src/logic/` 版，以调用方实际语义 `(Event, ShardId, Meta)` 为准重写保留版的字段映射（uid 取自 Meta），补一条不 meck 的端到端落库单测；CI 加「同 `-module` 名禁止多源文件」静态检查。
2. **分片一次性语义**：decrypt_shard 成功后置 `status='used'`（或冷却+次数上限+审计告警）；`remove_trusted_contact` 级联失效对应分片。
3. **注销级联**：`delete_all_related_data/2` 补删 `e2ee_social_shards`（含作为 proxy_uid 的）、`e2ee_trusted_contacts`、`e2ee_transfer_sessions`、`e2ee_local_backups`。
4. **恢复路径修通**：transfer 限制改为「同 uid 不同 device_id 允许」（需产品确认原语义）；backup 决策二选一——补 create 端点或删掉这套孤岛（表+2 API+repo）。
5. **cleanup 宽限**：accept 成功后延长 `expires_at`，窗口做成配置项。
6. **死代码清扫**：删 `create_key_shares/5`、`create_session/4`、`delete_restored_shards/2`（按死代码三闸标准当场重跑 xref 核实后删）；threshold 从请求体取真值并校验范围。
7. WS relay 三处在转发前查库核实 shard_id 归属（至少 decrypt_shard 路径）。

**建议修复顺序**：#1（审计链是其他一切监控的前提）→ #2+#3（真实安全敞口）→ #4（功能可用性）→ 其余。
