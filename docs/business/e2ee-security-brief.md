# imboy 端到端加密（E2EE）安全摘要

> 面向：企业 IT 决策者 / 安全审计方
> 版本：2026-07（2026-09-09 当前事实对账修订） | 产品等级：Preview（私有化部署） | 当前发布姿态：**NO-GO**（见文末「当前证据与发布状态」）

---

## 一句话定位

imboy 为**真人 C2C 与 C2G 消息**提供客户端端到端加密：真人消息在发送方设备加密、接收方设备解密，服务端在这些路径上设计为只接触密文和必要元数据。**与 AI 助手的 C2C 会话是明确披露的非 E2EE 明文处理通道**（见下文「AI 助手明文通道披露」），不属于端到端加密声明范围。

---

## 安全范围（先读）

| 消息域 | required / compliance 下的内容路径 | 服务端或第三方可见性 |
|---|---|---|
| 真人 C2C | Olm/PFv3 per-device E2EE | 设计为仅见密文和元数据；真实 DB/日志/Push/备份 Canary 复测待授权 |
| 真人 C2G | Megolm E2EE，room key 经 Olm 分发 | 同上；新成员/重入/新设备的群历史语义待产品决策（E2EE-2026-012） |
| AI 助手 C2C | 明文消息与明文附件（设计内） | server/staging/archive 可见正文；对象存储可见未封装附件；LLM provider 可见送入模型的正文与所选上下文 |
| optional / disabled | 非 E2EE（部署方自选） | 服务端可见明文，属部署选择，不属于 E2EE 声明 |

## 核心安全属性（当前准确表述）

| 属性 | 含义 | 对标 |
|------|------|------|
| 端到端加密 | 真人消息在发送方设备加密、接收方设备解密，服务端仅转发密文 | Signal / Matrix |
| 前向保密 (PFS) | C2C Olm Double Ratchet 提供协议属性；C2G Megolm rotation 不等于 Double Ratchet PCS | Signal Protocol §3 |
| 攻破后愈合 (PCS) | C2C 会话被攻破后，下一次 DH 交换即自动愈合 | Signal Protocol §4 |
| 降级防护 | 固定协议套件（C2C=Olm / C2G=Megolm），运行时不协商降级；HWM 高水位降级拦截为规划中机制，未接线 | — |
| 篡改与重放防护 | 认证信封、持久 message-id 与受保护信封 digest（当前 Base C 级回归全绿，真实攻击复测待授权） | — |
| 身份认证 | Ed25519 签名 + TOFU 固定 + 安全码（60 位指纹）比对 | Signal Fingerprint v2 |

## 服务端零知识保证（7 条不变量，仅适用于真人 E2EE 域）

以下不变量只覆盖真人 C2C/C2G 的 required/compliance 路径，**不适用于 AI 助手 C2C、`optional/disabled`、用户显式举报摘录或 compliance 私钥持有者**：

1. 不存储明文私钥——用户私钥从未离开用户设备
2. 不解密消息——密文作为不透明字节流路由
3. OTK 原子消费——一次性预密钥 FIFO + 行锁，防重放
4. CI 密码学门禁——任何服务端解密代码引入即刻构建失败
5. 推送不泄密——离线推送仅含"发来一条消息"，密文不入推送通道
6. 错误不泄密——API 错误返回不透明 `internal_error`，数据库 schema 不外露
7. 群消息透传——C2G 加密字段全链路 byte-for-byte 不修改

## AI 助手明文通道披露（必读）

与启用中的 AI 助手（`account_type=1`）对话时，消息和附件**不是端到端加密的**：客户端在发送前跳过封装，服务端与 LLM provider 按各自访问控制处理明文。这是产品功能设计，不是加密缺陷；部署方有义务在隐私政策中向最终用户披露。

**当前存在的未解决 HIGH 风险（LT02-SEC-01，release NO-GO 独立原因）**：客户端用于判断"对端是 AI"的 `peerAccountType=1` 标记目前来自普通 API 响应和本地通讯录存储，缺乏密码学签名或发送前用户确认。恶意服务端响应、本地数据库污染或错误同步理论上可把真人标记为 AI，使真人消息在离开设备前跳过加密。在发送前不可伪造的 AI 身份绑定、用户显式确认机制落地之前，本摘要不对"真人消息绝不可能被降级为明文"作任何承诺。

## ⚠️ 合规密钥托管：必读披露

**如果贵司启用 `compliance` 模式，消息将不再是纯端到端的。** 这一节我们主动写明，
而不是等尽调时被问出来。

### 机制

`e2ee_mode` 有四个取值，**出厂默认：community 版为 `optional`（当前实现等价于关闭，见下方说明）、enterprise 版为 `disabled`**，即默认部署下消息为明文，加密与合规托管**必须由部署方在管理后台显式开启**：

| `e2ee_mode` | 谁能读到明文 |
|---|---|
| `disabled` | E2EE 关闭，不适用 |
| `optional` | 同上（当前实现等价于关闭，见下方说明） |
| `required` | **仅收发双方设备**。纯端到端，无第三方通道 |
| `compliance` | 收发双方设备 **+ 持有合规私钥的审计方** |

在 `compliance` 模式下，客户端加密每条消息时，除了用各接收设备的公钥 wrap 一份 AES 会话密钥，
**还会额外用一枚"合规公钥"再 wrap 一份**，作为 `did: compliance-audit` 条目写入消息。
持有对应合规私钥的人，因此可以解密该模式下的**全部**消息。

### 这与"服务端零知识"是否矛盾

**不矛盾，但你需要理解边界**：

- 合规私钥由**审计方在本地（HSM / 离线介质）自行生成**，**永不上传服务端**。
  服务端只接收公钥（`compliance_key` 表已 `DROP COLUMN private_key_encrypted`）。
- 因此**服务器被完全攻破，攻击者仍拿不到合规私钥**，也就解不开消息 —— 零知识宣称成立。
- 但**持有合规私钥的那个人（组织内的审计员）能读全部消息**。
  纯端到端语义在这个模式下确实被打破了，这是设计意图，不是缺陷。

### 部署方的责任

1. **在隐私政策中向最终用户披露**该托管机制 —— 这是部署方的法定义务，不是我方代办事项。
2. **指定合规私钥的保管责任人、离线介质存放位置与访问审计流程。**
3. ⚠️ **私钥丢失不可恢复**：服务端不存任何私钥副本，合规私钥一旦丢失，
   用该公钥加密过的全部历史密文**永久无法通过合规通道解密**。
4. **不需要合规托管就别开**：配置 `required` 即为纯端到端，不产生第二收件人。

> `optional` 的已知设计债务：客户端本地开关目前硬编码为关闭，该模式实际等价于不加密。
> 需要加密请直接用 `required` 或 `compliance`。
