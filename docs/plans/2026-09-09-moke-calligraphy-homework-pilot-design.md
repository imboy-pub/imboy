# 墨课：书法视频作业 AI 回课助手设计

> 状态：草案，供校对与修改
>
> 日期：2026-09-09
>
> 推荐路线：你姐姐所在机构、一个班级真实试点
>
> 产品边界：按单机构试点交付，但核心数据和权限边界不得堵死未来多机构 SaaS

---

## 1. 决策摘要

本产品不定位为“AI 自动给孩子书法打分”，而定位为：

> **书法老师的 AI 视频回课助手。**

家长继续拍摄孩子练字视频；系统先整理作业、抽取关键画面并生成点评草稿；老师核对后录制或上传真人点评视频；最终结果私密返回给对应家长。AI 负责减少重复劳动，老师保留最终专业判断和发布权。

首版建议：

1. 先服务你姐姐所在机构的一个真实班级，不先建设完整 SaaS。
2. 家长端目标载体是微信小程序，但在正式开发前可先用交互原型或微信内 H5 验证流程。
3. IMBoy 是业务主后端，持有用户、机构、班级、作业、附件、权限、通知和最终点评。
4. AI 分析由 IMBoy 后端内部的异步任务和模型适配层完成，不引入 DeepFlux 运行时或跨系统依赖。
5. 不新建第三套业务后端；新 Git 仓库只用于家长端小程序。
6. “墨课”等新品牌只落在新客户端；服务端代码、产品身份和运维主体仍是 IMBoy。
7. 新品牌域名和 `pro.imboy.pub` 最多作为同一组 IMBoy API 的入口，不部署品牌专属后端。
8. Workspace 对应机构，Group 承载班级沟通空间，现有 Group Task 复用为作业任务。
9. 家长是可登录用户；低龄学员首版是受监护的教学档案，不强制创建独立账号。
10. 学生视频默认仅绑定家长和授权老师可见，不再默认发布到整个微信群。

## 2. 需求背景

### 2.1 当前真实流程

机构老板目前要求老师在微信群内完成视频互动：

1. 家长拍摄约一分钟的孩子练字视频。
2. 家长把视频发送到班级微信群。
3. 老师逐条寻找、观看学生视频。
4. 老师根据视频中的问题组织点评内容。
5. 老师再拍摄约一分钟的讲解视频。
6. 老师把点评视频发回微信群。

这个流程保留了真人老师的可信度，但存在大量非教学劳动：找视频、核对学生、记录完成情况、重复归纳同类问题、重新组织口播语言、追踪漏交和漏评。

### 2.2 主要问题

- 视频散落在聊天记录中，无法形成稳定的作业队列。
- 老师无法快速看到“待交、AI 分析中、待点评、已回评、需重练”。
- 同类问题需要为每名学生重复组织语言。
- 家长难以回看历次作业和老师建议。
- 单个孩子的视频默认对整个群可见，隐私边界过宽。
- 微信群不能可靠承载作业状态、权限、审计、删除和成长记录。
- 现有“墨韵”Demo偏完整作品图片评分，不覆盖视频提交、老师审核和视频回评闭环。

### 2.3 产品机会

产品价值不应是“让 AI 代替老师”，而应是：

- 让老师直接进入按优先级排列的待点评队列。
- 让 AI 预先整理视频观察点和口播提纲。
- 让老师用最少操作完成核对、修改、录制和发送。
- 让家长只看到经过老师确认的清晰建议。
- 把共性问题汇总成班级讲解，同时保护单个学生隐私。

## 4. 目标用户与核心任务

### 4.1 机构负责人

核心任务：建立班级、安排老师、查看交作业和回评进度、控制数据与人员权限。

### 4.2 老师/助教

核心任务：发布作业、快速查看视频、核对 AI 草稿、录制真人回复、要求重练、归纳班级共性问题。

### 4.3 家长

核心任务：替孩子接收作业、提交视频/照片、查看老师回复、根据建议安排下一次练习。

### 4.4 学员

核心任务：完成练习并看到简单、具体、不过载的反馈。低龄学员不必直接操作账号。

## 5. 产品原则

1. **老师最终负责。** AI 结果永远是草稿，不得自动作为老师点评发布。
2. **一次先改一处。** 家长端不堆满逐字分数，优先呈现一个最重要的改进动作。
3. **作业不是群消息。** 作业可以产生通知，但作业状态和学生视频必须存入结构化业务对象。
4. **默认私密。** 单个学生的提交和回评仅对授权老师和绑定监护人可见。
5. **失败不阻断人工。** AI 超时或失败时，老师仍可直接人工点评。
6. **先复用再新增。** 复用 IMBoy Workspace、Group、Group Task、附件和消息能力。
7. **试点范围，SaaS 边界。** 首版不建设商业平台，但所有教学数据必须存在明确的 Workspace 归属。
8. **证据优先。** 离线 Demo、提示词和模型 JSON 不等于真实学生场景下的评测准确性。

## 6. IMBoy 对象映射

| 产品概念 | IMBoy 现有对象 | 处理方式 |
|---|---|---|
| 培训机构 | Workspace | 直接作为机构和数据边界 |
| 班级沟通空间 | Group | 复用聊天、公告、成员和通知能力 |
| 班级教学属性 | 无完整对象 | 新增轻量 `class_profile`，以 `group_id` 为主键 |
| 作业任务 | `group_task` | 直接复用标题、说明、截止时间、创建者和状态 |
| 作业分配 | `group_task_assignment` | 保留现有流程，扩展学员归属和提交审计 |
| 视频/照片 | Attachment + Garage | 复用直传、鉴权和短时访问 URL |
| 老师最终反馈 | 现有评论字段不足 | 新增结构化老师回评对象和视频附件关系 |
| AI 执行任务 | IMBoy 内部异步任务 | 复用模型提供商适配能力，运行状态与教学结果分离 |
| 家长微信身份 | `sso_identity` 可复用模式 | 增加微信小程序 provider 的登录绑定流程 |

### 6.1 Workspace 是否等于机构

可以。当前 Workspace 已经是组织级访问边界，不需要再创建一层 Organization。

但首版即使只有一个机构，也不能把机构 ID 写死在全局业务逻辑中。应由登录身份、班级邀请或部署配置解析当前 Workspace，并在所有查询中进行权限校验。

### 6.2 Group 是否等于班级

Group 可以作为班级的沟通容器，但不应独自承担完整班级语义。

建议增加：

```text
class_profile
- group_id          PK/FK -> group.id
- workspace_id      FK -> workspace.id
- name
- term
- course_type       hard_pen | brush | mixed
- status            active | archived
- created_at
- updated_at
```

这样可继续复用 Group 聊天和公告，同时避免把课程类型、学期、任课老师等业务字段塞进通用群表。

### 6.3 Group 角色能否直接表示老师、家长和学员

不能。

现有 Group 角色是聊天治理权限：普通成员、嘉宾、管理员、群主、副群主。管理员角色还包含踢人、禁言、发公告等能力。教学身份是业务关系，两者不能混用。

建议拆分：

```text
class_staff
- group_id
- user_id
- role              manager | teacher | assistant
- status

learner
- id
- workspace_id
- display_name
- birth_year        可选；非必要不收集完整生日
- user_id           可空；未来注册 IMBoy 账号后绑定，同一 Workspace 内唯一
- account_bound_at  可空
- account_bound_by  可空；记录确认绑定的监护人或管理员
- status

class_enrollment
- group_id
- learner_id
- status
- joined_at

guardian_learner
- guardian_uid
- learner_id
- relation          guardian | other
- can_submit
- can_view_review
- status
```

家长可以同时是普通 Group Member，但其查看学员作业的权限必须来自 `guardian_learner`，不能仅凭“在同一个群”获得。

## 7. 家长和学员账号设计

### 7.1 推荐结论

家长与学员是两个业务主体，但第一版不要求两个登录账号。

- 家长：IMBoy 人类用户，绑定微信小程序身份。
- 学员：拥有稳定 `learner_id` 的独立教学档案，由监护人代为操作。
- 一个家长可绑定多个孩子。
- 一个孩子可绑定多位监护人。
- `learner.user_id` 首版为空；绑定后在同一 Workspace 内保持唯一，可用 `(workspace_id, user_id)` 的部分唯一约束实现。
- 年龄较大或确有独立操作需求时，学员注册正常 IMBoy 账号，再经监护人确认把该账号绑定到原 `learner`。
- 绑定后，历史作业、老师回评和成长记录仍以原 `learner_id` 为归属；账号只是新增登录入口，不复制、不迁移历史数据。
- 解绑或更换账号时只改变登录关系，不删除学员档案和历史记录；具体申诉与重新绑定流程在正式开放学员注册前实现。

### 7.2 未来账号绑定流程

建议预留以下流程，首版只实现数据结构，不必开放学员端界面：

1. 学员使用手机号、微信或其他受支持方式注册正常 IMBoy 用户。
2. 学员输入由监护人或机构生成的短期绑定码，不能仅凭姓名搜索并认领档案。
3. 已绑定监护人在自己的端内确认，必要时由授权老师或机构管理员复核。
4. IMBoy 校验目标 `learner` 尚未绑定账号，且该用户在当前 Workspace 内未绑定其他学员档案后，写入 `learner.user_id`、绑定时间、确认人和审计事件。
5. 学员登录后按权限查看自己的历史作业、已发布回评和成长记录；不得看到监护人的私有信息、老师 AI 草稿或其他学员数据。

需要记录绑定方式和解绑审计。同一 Workspace 内，学员参加多个班级时应复用一个 `learner`；跨机构时，各 Workspace 保持独立的学员档案和数据权限，但可以绑定同一个 IMBoy 用户。学员登录后可按授权切换机构并查看各自历史，不得通过账号绑定打通机构间后台权限或让一家机构读取另一家的数据。

### 7.3 为什么不能让家长和孩子共用一个业务主体

共用会导致：

- 无法区分“谁完成练习”和“谁执行上传”。
- 一个家长有两个孩子时无法正确分配同一份作业。
- 成长记录会落到家长账号而不是孩子档案。
- 监护关系、删除请求和可见权限无法准确表达。

### 7.4 对现有 Group Task Assignment 的最小扩展

现有唯一约束是 `(task_id, user_id)`。建议：

- `user_id` 继续表示接收任务、负责提交的账号；
- 增加可空 `learner_id` 表示作业实际归属的学员；
- 增加 `submitted_by` 记录真实提交人；
- 普通 IMBoy 群任务保持 `learner_id IS NULL`；
- 教学作业按 `(task_id, learner_id)` 保证唯一；
- 不创建“每个孩子一个假手机号/假用户”的数据。

具体约束应在实现计划阶段结合现有数据迁移做兼容设计，本文不直接拍迁移编号。

## 8. 家长微信小程序信息架构

### 8.1 底部导航

```text
作业 | 成长 | 我的
```

首版不在小程序中复制完整 IM 聊天能力。班级通知、作业和回评是主要功能；普通沟通暂时留在微信或 IMBoy。

### 8.2 作业首页

```text
┌────────────────────────────┐
│ 小禾 · 硬笔启蒙三班      [切换学员] │
│ 待完成 1   待点评 1   已完成 12     │
├────────────────────────────┤
│ 本周作业：横画与重心               │
│ 截止：周五 20:00                   │
│ 要求：书写视频 + 成品照片           │
│                    [拍摄并提交]     │
├────────────────────────────┤
│ 老师已回评：第 8 次练习             │
│ [视频封面] 本次先改：横画稍上斜     │
│                    [查看点评]       │
└────────────────────────────┘
```

要求：

- 第一屏直接展示真实作业，不做营销 Hero。
- 主操作始终是“拍摄并提交”或“查看老师点评”。
- 状态文字和颜色同时表达，不只依赖颜色。
- 多个孩子时在顶部切换学员，默认记住上次选择。

### 8.3 作业详情

信息顺序：

1. 作业标题和截止时间；
2. 老师示范视频或示范图片；
3. 本次只关注的教学重点；
4. 提交要求：视频、照片或两者；
5. 历次提交和老师要求重练记录；
6. “开始拍摄”主按钮。

### 8.4 拍摄与提交

只保留三步：

1. 确认学员；
2. 拍摄/选择约一分钟视频，可补拍一张完整作品照片；
3. 预览、确认并提交。

拍摄提示：

- 只拍手、笔和纸即可，避免拍摄孩子正脸；
- 保持光线均匀，纸张完整进入取景框；
- 手机尽量固定，避免遮挡笔尖；
- 结束前停留一至两秒展示完整作品；
- 作业可配置 `video_only`、`photo_only` 或 `video_and_photo`，首版不做任意媒体规则编辑器。

上传体验：

- 显示压缩、上传和提交三个独立状态；
- 支持进度、取消和失败重试；
- 上传中离开页面后可以恢复状态；
- 服务端异步分析，不要求家长停留等待；
- 重复点击提交必须幂等；
- 文件过大时先给出明确处理建议，不在最后一步才报错。

### 8.5 回评详情

展示优先级：

1. 老师真人点评视频；
2. “这次做得好”的一处；
3. “本次先改”的一个问题；
4. 下一次可执行练习；
5. 老师要求重练时的重新提交入口；
6. 折叠的“专业分析”。

“专业分析”可复用墨韵评测引擎的逐字结果、关键字和维度信息，但默认不向家长展示大面积雷达图和几十个分数。

### 8.6 成长页

首版只展示经过老师确认的数据：

- 已完成作业数量；
- 老师反复提到的练习主题；
- 代表作品；
- 最近一次与上一次的老师总结。

在没有真实评测一致性证据前，不展示精确的“能力增长 17%”或自动排名。

### 8.7 我的

- 学员管理；
- 监护关系；
- 班级与老师；
- 通知设置；
- 儿童信息处理规则和监护人同意记录；
- 查看、下载或删除孩子数据的入口；
- 原始视频保留期限说明。

## 9. 视觉与交互方向

### 9.1 视觉语言

- 主色：墨黑、纸白、印章红；状态成功可使用克制的绿色。
- 不使用大面积棕色、米色和仿古纹理统治整个界面。
- 书法字体只用于品牌字或少量标题，正文使用清晰的系统字体。
- 卡片圆角保持 8px 以内，避免层层套卡片。
- 操作页面以清晰、安静、易扫描为主，不做比赛展示页式的大 Hero。

### 9.2 关键控件

- 拍摄、播放、暂停、删除使用熟悉的图标并提供文字或 tooltip/无障碍标签。
- 作业状态使用标签：待完成、上传中、AI 分析中、待老师点评、已回评、需重练。
- 视频区域使用稳定宽高比，加载、失败和处理中不能造成布局跳动。
- 主要按钮放在单手易触达区域，点击区域满足移动端可用性。
- 所有长标题、班级名和学员名必须在窄屏下换行或省略，不得遮挡操作。

### 9.3 对现有墨韵 Demo 的处理

保留：

- 真实字迹切割；
- 重点字拆解；
- 结构化模型输出；
- 老师可展开查看的专业分析。

调整：

- 首页不再是介绍页；
- 报告不再以总分和雷达图为核心；
- 不把 AI 输出直接称为老师结论；
- 桌面居中长卡片改为移动端任务流；
- 一次突出一个改进动作。

## 10. 老师端 IMBoy 工作流

### 10.1 Workspace 导航

在机构 Workspace 中增加“教学”入口，包含：

- 待点评；
- 作业；
- 班级；
- 学员；
- 共性问题。

不要求首版重做完整 IMBoy 导航，只需提供一个稳定入口和待点评数量。

### 10.2 待点评队列

每条显示：

- 学员名；
- 班级；
- 作业名称；
- 提交时间；
- 视频时长；
- AI 状态；
- 是否逾期；
- 当前负责老师。

默认按提交时间排序，可按班级和作业筛选。老师处理完成后自动进入下一份，减少来回跳转。

### 10.3 点评工作台

```text
┌──────────────────────────┬─────────────────────────┐
│ 学生视频 / 成品照片       │ 墨课助教草稿             │
│                          │ 主要问题：横画轻微上斜    │
│ [0:18] 握笔过紧          │ 证据时间点：0:18、0:42   │
│ [0:42] 横画收笔过快      │ 建议讲法：先慢写三遍……   │
│ 倍速  关键帧  全屏       │ [采用] [修改] [判断错误]  │
├──────────────────────────┴─────────────────────────┤
│ 口播提纲                                        │
│ 1. 先肯定坐姿  2. 演示横画  3. 布置三遍练习      │
│            [录制点评视频] [保存草稿] [审核并发送] │
└────────────────────────────────────────────────────┘
```

### 10.4 发布规则

- 老师必须主动点击“审核并发送”。
- 最终文本与视频记录 `reviewed_by` 和发布时间。
- 默认私密送达对应监护人。
- 只有在监护人另行授权后，才能将个体作品作为优秀案例公开。
- 老师可基于匿名汇总的共性问题录制班级讲解，并发布到 Group。
- AI 不得自行向家长发送消息。

### 10.5 多老师协作

现有 Group Task 主要限制为作业创建者批改，不满足机构负责人、任课老师和代课老师共同处理。

新规则应基于 `class_staff`：

- manager：管理班级和老师，可查看进度；
- teacher：可发布作业、查看提交、批改和发布；
- assistant：可预处理或保存草稿，是否可发布由机构策略决定；
- Group 管理员身份不能自动获得教学数据访问权。

## 11. 作业与回评状态

避免把所有状态塞进一个巨大枚举。沿用现有作业状态，并拆分 AI 与老师状态。

### 11.1 作业分配状态

沿用 `group_task_assignment.status`：

```text
0 待完成
1 进行中
2 已提交
3 已批改
```

### 11.2 AI 任务状态

```text
queued -> running -> succeeded
                  -> failed
```

AI 失败不修改作业分配为失败；作业仍然保持“已提交”，进入人工队列。

### 11.3 老师回评状态

```text
draft -> published
      -> discarded
```

若需要重练，发布结果中增加 `rework_required=true`，并生成下一次提交机会；不重置或覆盖原提交证据。

## 13. 后端架构

### 13.1 推荐责任边界

```text
微信小程序
    |
    | HTTPS/JWT
    v
IMBoy 后端
    |- 微信身份绑定
    |- Workspace/Group/教学权限
    |- Group Task/Assignment
    |- Garage 附件与短时 URL
    |- 老师最终回评
    |- WebSocket/通知
    |- 内部 AI 异步任务
        |- 视频转码与关键帧抽取
        |- 视觉模型适配器
        |- 提示词/评分规程版本
        |- JSON Schema 校验
        |- 结构化点评草稿
        |- 质量评估与老师反馈
```

### 13.2 为什么全部放在 IMBoy 后端

IMBoy 已有用户、Workspace、Group、群作业、视频附件、Garage S3、鉴权、消息、通知、LLM provider 注册表和 OpenAI 兼容适配器。教学 AI 首版只是“提交后异步生成结构化草稿”，没有必要为此部署 DeepFlux 或新建业务后端。

单后端可以减少一套部署、鉴权、队列观测、故障排查和数据删除链路。儿童视频及派生帧也不需要在两个业务系统间流转，权限和删除审计更容易闭合。

### 13.3 IMBoy 内部 AI 模块边界

不引入第二个服务，不等于把 AI 逻辑散落在作业 Handler 中。IMBoy 内部保持轻量模块边界：

- 作业 Logic 在提交成功后创建 AI 异步任务，不同步等待模型结果；
- AI Worker 只接收 `workspace_id`、`assignment_id` 和附件 ID，不把短时 URL 持久化到任务参数；
- Worker 从 Garage 读取授权附件，完成转码、抽帧和最小化处理；
- 视觉模型适配器复用现有 `imboy_llm` provider 注册模式，按模型能力扩展图片消息；
- 结构化结果通过 JSON Schema 校验后写入 `calligraphy_review_draft`；
- 老师审核发布仍走教学 Logic，不由模型适配器直接发送消息。

首版不要求模型直接理解完整视频流。现有 `imboy_llm_openai` 虽会原样转发 OpenAI 兼容的 `messages`，但图片输入、模型能力声明、超时和响应格式仍需在实现前做真实 provider 验证，不能仅凭接口形状视为已支持。

### 13.4 是否需要新后端仓库

不需要。

建议只新建小程序仓库，例如：

```text
moke-miniapp/
```

如果未来产品与 IMBoy 完全脱钩、需要独立团队和独立发布节奏，再评估拆分教学后端。当前没有这个证据。

### 13.5 IMBoy 内部 AI 任务载荷

内部队列只保存业务 ID 和版本，不持久化短时附件 URL：

```json
{
  "assignment_id": "...",
  "workspace_id": "...",
  "video_attachment_id": "...",
  "photo_attachment_id": "...",
  "rubric_version": "calligraphy-v1",
  "teacher_profile": "teacher-default-v1"
}
```

概念响应：

```json
{
  "job_id": "...",
  "status": "queued"
}
```

最终结构化结果：

```json
{
  "observations": [
    {
      "timestamp_ms": 18000,
      "category": "stroke",
      "text": "横画收笔偏快",
      "confidence": 0.73
    }
  ],
  "positive_point": "书写节奏较稳定",
  "focus_problem": "横画轻微上斜",
  "practice_action": "慢写三遍，起收笔各停一拍",
  "teacher_script": [
    "先肯定本次坐姿和完成度",
    "演示一次横画的行笔方向",
    "布置三遍慢写练习"
  ],
  "needs_human_attention": true
}
```

`confidence` 只用于提醒老师核对，不能作为面向家长的精确可信度宣传。

### 13.6 品牌与 API 域名

新品牌落在新客户端，服务端仍运行同一套 IMBoy 代码和同一组 API：

```text
墨课微信小程序 ─┐
                 ├─ 新品牌 API 域名（待定） ─┐
IMBoy 客户端 ────┤                         ├─ 同一套 IMBoy API 服务
                 └─ pro.imboy.pub ─────────┘
```

实现边界：

- 不复制 IMBoy 后端仓库，不启动“墨课专属”业务服务；
- 新品牌域名和 `pro.imboy.pub` 只是经 Caddy/Nginx 进入同一 API 集群的域名入口；
- API 路径、响应结构、错误码和鉴权协议保持一致，品牌客户端不维护私有 API 分支；
- 域名不是租户边界，不能根据 `Host` 直接推断 Workspace 或授予权限；
- Workspace 必须由已验证的用户身份、邀请/成员关系和请求上下文解析；
- 登录回调白名单、CORS、JWT audience、限流、审计和指标应显式识别客户端 `client_id`/渠道，不能只依赖域名；
- Garage 上传与查看仍使用 IMBoy 的鉴权和短时 URL，不为品牌客户端开放公共对象地址；
- TLS 证书、DNS、微信公众平台 request/upload/download 合法域名和生产配置属于上线动作，实施前另行人工确认。

如果后续确实需要不同机构展示不同 Logo，优先复用 Workspace 级品牌配置；不要为每个机构新增域名或复制一套后端。

## 14. AI 处理流程

```text
家长提交
-> IMBoy 校验作业、学员和监护权限
-> Garage 对象确认并绑定作业
-> 创建异步 AI 任务
-> 视频转码/抽取代表帧和最终成品帧
-> 去除姓名、班级等非必要业务信息
-> IMBoy 内部 Worker 通过模型适配器调用视觉模型
-> JSON Schema 校验
-> 保存 AI 草稿、模型和规则版本
-> 老师审核、修改或标记错误
-> 老师录制真人视频
-> IMBoy 发布最终回评
-> 家长收到通知并查看
```

### 14.1 AI 草稿内容

- 一至三个带时间点的观察；
- 一个优点；
- 一个优先改进问题；
- 一个可执行练习动作；
- 约 30 至 60 秒的老师口播提纲；
- 需要老师重点核对的疑点；
- 可选的逐字图片分析。

### 14.2 AI 不做的事

- 不直接发布点评；
- 不给学员做公开排名；
- 不根据一次视频做能力定性；
- 不把推测的握笔、性格或态度当成事实；
- 不在没有清晰画面的情况下输出确定性书法问题；
- 不把学生视频用于模型训练，除非另有明确、单独且可撤回的合法授权和供应商约束。

### 14.3 失败处理

- 转码失败：保留原视频给老师，提示重新处理或人工点评。
- 模型超时：任务可重试，老师队列不被阻断。
- Schema 不合格：不展示半结构化结果，记录稳定错误码。
- 置信度低：标记“需重点核对”，不自动重试多个模型消耗成本。
- 老师判定 AI 错误：记录错误类别和最终修改，不覆盖原草稿。

## 15. 权限与隐私

### 15.1 基本原则

不满十四周岁未成年人的个人信息属于敏感个人信息。视频可能包含面部、声音、家庭环境和行为信息，必须按最小必要原则处理。

### 15.2 默认可见范围

| 数据 | 可见对象 |
|---|---|
| 作业要求 | 班级成员 |
| 学生提交视频/照片 | 绑定监护人、授权老师/助教 |
| AI 草稿 | 授权老师/助教，不对家长开放 |
| 老师已发布回评 | 绑定监护人、授权老师 |
| 匿名共性问题 | 班级成员 |
| 优秀作品公开展示 | 仅另行授权后的范围 |

### 15.3 必须具备

- 显著的监护人告知与同意；
- 拒绝选项；
- 收集目的、处理方式、保存地点和期限说明；
- 更正、撤回和删除入口；
- 工作人员最小授权；
- 访问与发布审计；
- 短时签名 URL，不存永久公开地址；
- 原视频自动清理策略；
- 第三方模型供应商清单和处理边界；
- 停止服务时的数据处理方案。

### 15.4 建议的产品默认值

- 拍摄引导默认要求只拍手和纸；
- 原始视频使用短周期保留，具体天数由试点机构与合规意见确认；
- 成长档案优先保留老师最终评语和家长主动选择的代表作品；
- 向 AI 发送的帧不携带学员真实姓名；
- 不在班级群默认公开个体作业和回评；
- 监护人删除请求必须级联处理派生帧和未必要保留的 AI 输入。

## 16. 单班试点与多机构 SaaS 的差异

### 16.1 一句话结论

两种路线的家长提交、AI 起草、老师审核、视频回评核心流程基本相同；差异最大的不是作业页面，而是多租户治理、机构自助配置、计费、配额、运营、支持、合规和部署体系。

如果一开始做完整 SaaS，不是多写几个机构管理页面，而是额外建设一层平台产品。它会明显推迟第一次真实老师使用，并增加大量尚未得到市场验证的代码。

用于方案比较的粗略工程量级（不是排期承诺）：

| 路线 | 相对首发工作量 | 说明 |
|---|---:|---|
| 一次性单班 Demo | 0.7–0.9 | 最快，但容易省掉租户、权限、审计和迁移边界，不推荐作为产品基线 |
| 单班真实试点 + SaaS 边界建模 | 1.0 | 推荐基线；做对 Workspace、角色、学员、附件和回评归属 |
| 在推荐基线上提前补少量多机构能力 | 1.2–1.4 | 增加机构切换、基础配置和更完整隔离测试，但不做计费、白标和平台运营 |
| 完整多机构 SaaS 首发 | 2.0–3.0 | 增加自助开通、租户治理、计费、配额、运营、客服、退出和合规体系 |

持续运维复杂度的差距通常比首发开发更大：单机构试点可视为 `1.0`，面向多家机构并承诺稳定服务后，监控、故障定位、租户迁移、账单、客服和 SLA 可能达到 `3–5` 倍。具体数值必须在明确部署模式、付费方式和服务承诺后重新估算。

### 16.2 逐项比较

| 维度 | 单机构单班试点 | 多机构 SaaS 首发 | 差异程度 |
|---|---|---|---|
| 家长作业流程 | 固定班级、邀请进入 | 多机构、多班级、跨机构切换 | 低 |
| 老师点评流程 | 固定老师或少量代课老师 | 多角色、调岗、离职、跨班协作 | 中 |
| 机构创建 | 运维或项目方手工创建 | 机构自助注册、试用、开通、注销 | 高 |
| 租户隔离 | 一个 Workspace，但仍做边界校验 | 所有查询、缓存、任务、对象存储严格按租户隔离 | 高 |
| 权限 | 固定 manager/teacher/assistant | 租户管理员、岗位、细粒度授权、审计 | 高 |
| 微信身份 | 一个小程序、固定业务配置 | 多机构邀请、渠道归因、账号合并与申诉 | 中 |
| AI 配置 | 一套老师规则和模型配置 | 每机构模型、提示词、预算、禁用策略、版本回滚 | 高 |
| 数据保留 | 与试点机构人工确认 | 每租户策略、批量导出、删除 SLA、合同约束 | 高 |
| 品牌 | 新客户端使用墨课品牌，服务端仍为 IMBoy | 白标、机构 Logo、主题和自定义域名 | 高，但可延期 |
| 计费 | 不做或线下结算 | 套餐、席位、用量、账单、退款、欠费降级 | 很高 |
| AI 成本 | 人工观察单班成本 | 配额、限流、成本归因、异常用量和防滥用 | 高 |
| 运维 | 单实例、人工支持 | 租户级监控、告警、限流、迁移、支持工具 | 很高 |
| 客服支持 | 直接联系试点老师 | 工单、审计检索、租户诊断、SLA | 高 |
| 合规责任 | 单一明确试点范围 | 多机构合同、处理者角色、供应商和地域差异 | 很高 |
| 上线验收 | 一个班真实闭环 | 多机构并发、隔离、计费、退出和恢复验证 | 很高 |

### 16.3 两种路线不应不同的部分

即使只做一个班，以下边界也必须从第一天正确：

1. 每条教学数据都直接或通过可靠外键归属 Workspace。
2. 教学角色与 Group 治理角色分离。
3. 家长账号与学员档案分离。
4. 作业提交与普通群消息分离。
5. AI 草稿与老师最终回评分离。
6. AI Worker 与教学业务通过内部任务载荷和模块边界连接。
7. 附件默认私密，访问必须鉴权。
8. 模型、提示词和评分规则可追溯。
9. 删除、撤回和审计从数据模型开始保留落点。
10. 业务配置不得只存在代码中的全局常量，应至少允许 Workspace 级覆盖真正会变化的值。

做好这些基础，试点转 SaaS 时主要增加平台治理层，而不是推翻作业核心。

### 16.4 单班试点刻意不做的 SaaS 能力

- 机构自助注册和开通；
- 在线订阅计费；
- 套餐和 AI 用量结算；
- 白标和自定义域名；
- 任意自定义角色/RBAC 编辑器；
- 飞书和钉钉端；
- 多区域部署；
- HA 和自动扩缩容；
- 复杂运营后台；
- 机构间数据迁移；
- 面向销售的试用漏斗；
- 完整客服工单与 SLA；
- AI 模型市场；
- 学员排名和比赛系统。

### 16.5 何时从试点升级为 SaaS

建议同时满足以下证据后再启动 SaaS 平台层：

- 一个真实班级完成连续多轮作业闭环；
- 老师的单份点评耗时相对基线明确下降；
- 多数 AI 草稿达到“可采用或轻改”而不是全部重写；
- 家长视频提交成功率和查看回评率可接受；
- 未出现严重越权、错误公开或数据删除失败；
- 至少有第二家机构表达明确试用或付费意愿；
- 第二家机构的流程差异能够被现有领域模型承载，而不是完全不同的产品。

这里不预设漂亮百分比。先记录当前微信群流程的真实基线，再和试点数据比较。

## 17. 是否一定做微信小程序

### 17.1 推荐答案

长期家长端优先微信小程序，短期验证不必从小程序工程开始。

推荐顺序：

```text
交互原型
-> 微信内 H5 或最小小程序验证上传闭环
-> 一个班真实试点
-> 根据真实失败点完善正式微信小程序
-> 出现明确客户需求后再适配飞书/钉钉
```

### 17.2 为什么不先做三端统一

微信、飞书和钉钉都能承载轻应用，但身份、媒体选择、文件上传、通知、审核和发布机制不同。可复用的应是：

- IMBoy API；
- 领域状态；
- JSON Schema；
- 设计 Token；
- 页面信息架构；
- 平台适配接口。

不应提前承诺一套前端代码完全无差异运行三端。当前提供的初赛目录只有离线 HTML Demo、图片和 JSON；文档虽然提到 UniApp 迁移，但没有随目录提供可审计的小程序源码，不能把它当作已存在的生产代码基线。

## 19. 试点方案

### 19.1 试点对象

- 你姐姐所在机构；
- 一名主要老师；
- 一个真实班级；
- 经监护人明确同意参与的家庭；
- 不把含真实儿童信息的样本加入 Git 仓库或普通开发日志。

### 19.2 先记录基线

在上线前记录当前微信群流程：

- 每份作业从找到视频到发出回复的耗时；
- 每周提交数量；
- 漏交和漏评情况；
- 老师最常重复的点评类型；
- 家长常见拍摄和上传问题；
- 老师认为最难由 AI 判断的内容。

### 19.3 试点指标

核心指标：

- 老师每份作业中位处理时间；
- AI 草稿采用、轻改、重写、错误四类占比；
- 老师修改前后的差异和错误类别；
- 家长上传成功率；
- 家长查看回评率；
- 作业从提交到回评的时间；
- 要求重练后的再次提交率；
- 越权访问、错误公开、删除失败等严重事件数。

### 19.4 Go / No-Go

Go：

- 老师愿意持续使用待点评工作台；
- 实际处理时间下降；
- AI 草稿多数不需要完全重写；
- 家长能够独立完成上传和查看；
- 隐私与权限检查通过；
- 第二家机构存在明确需求。

No-Go 或需要重做：

- 老师处理时间没有下降；
- AI 错误导致核对成本高于自行点评；
- 家长仍坚持只在微信群交作业且不愿进入新入口；
- 视频质量普遍不足以支持分析；
- 个体视频公开和数据删除边界无法落实；
- 产品价值最终只是“生成一段泛泛评语”。

## 20. 测试与证据分级

### 20.1 自动化测试

- Workspace、Group、教学身份和监护关系权限矩阵；
- 一个家长关联多个学员；
- 一个学员关联多个监护人；
- 同一任务下同一家长替多个孩子提交；
- 附件绑定、访问和删除；
- 重复提交幂等；
- AI 超时、失败和 Schema 错误；
- 老师无权批改、助教无权发布；
- 未发布 AI 草稿不能被家长读取；
- 归档 Workspace/班级禁止继续写入；
- 日志不得出现短时 URL、儿童姓名或媒体内容。

### 20.2 真机验证

- 微信内登录和身份绑定；
- Android 与 iOS 微信客户端拍摄/选择视频；
- 弱网、断网和后台恢复；
- 大文件压缩和上传；
- 视频播放、横竖屏和静音；
- 老师端录制视频；
- 通知打开后定位到正确作业；
- 监护人删除路径。

### 20.3 人工质量验证

- 使用获得授权且去标识的样本；
- 老师在不知道 AI 输出来源的情况下评价草稿；
- 分开记录“观察是否正确”和“话术是否好用”；
- 同一视频重复运行检查稳定性；
- 不用离线 Demo 的一次成功结果替代真实班级证据。

### 20.4 证据标签

- `LOCAL PASS`：本地测试或静态检查通过；
- `DEVICE PASS`：指定真实设备流程通过；
- `TEACHER PASS`：真实老师对匿名/授权样本认可；
- `PILOT PASS`：真实班级完成连续闭环；
- `BLOCKED`：缺少账号、设备、授权、真实样本或外部审核；
- `NO-GO`：隐私、权限或产品价值存在不可接受问题。

## 24. 当前建议

选择“你姐姐所在机构、一个班级真实试点”，但不是做一次性 Demo。

首版把以下五件事做对：

1. Workspace 数据边界；
2. 家长、学员和教学角色关系；
3. 作业、提交和老师回评的结构化闭环；
4. AI 草稿与老师发布权分离；
5. 儿童视频默认私密、可删除、可审计。

这五项正确，未来转多机构 SaaS 不需要推翻核心；需要新增的是机构自助开通、租户治理、计费、配额、运营、合规和标准交付。现在提前建设这些平台能力，会延迟最重要的证据：你姐姐是否真的因此少花时间、家长是否真的愿意使用、AI 草稿是否真的比老师自己想更省事。
